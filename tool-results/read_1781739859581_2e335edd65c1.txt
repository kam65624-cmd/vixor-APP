     1→# QuantDinger v3 Python Strategy Development Guide
     2→
     3→This guide is written from a **developer** point of view. Its goal is not only to list the current contracts, but to answer the practical question:
     4→
     5→**How do I build an indicator strategy that is clear, backtestable, and ready to become a saved trading strategy?**
     6→
     7→QuantDinger currently supports two Python authoring models:
     8→
     9→- **IndicatorStrategy**: dataframe-based code for indicator research, chart rendering, and signal-style backtests.
    10→- **ScriptStrategy**: event-driven code for runtime execution, strategy backtests, and live trading.
    11→
    12→If you are starting a new strategy, the default recommendation is:
    13→
    14→1. Start with `IndicatorStrategy`.
    15→2. Prove the signal logic visually and in backtests.
    16→3. Move to `ScriptStrategy` only if you need bar-by-bar state, dynamic position management, or execution control.
    17→
    18→---
    19→
    20→## 1. Start With the Right Mental Model
    21→
    22→The most common source of confusion is mixing up **signal logic**, **risk defaults**, and **runtime execution**.
    23→
    24→### 1.1 IndicatorStrategy
    25→
    26→Think of `IndicatorStrategy` as:
    27→
    28→- compute indicator series from `df`
    29→- generate boolean `buy` / `sell` signals
    30→- declare default strategy settings through metadata comments
    31→- return chart-friendly `output`
    32→
    33→This is the best fit for:
    34→
    35→- indicator research
    36→- strategy prototyping
    37→- parameter tuning
    38→- signal-based backtests
    39→- saved strategies that still follow a signal-first workflow
    40→
    41→### 1.2 ScriptStrategy
    42→
    43→Think of `ScriptStrategy` as:
    44→
    45→- maintain runtime logic bar by bar
    46→- inspect current position state through `ctx.position`
    47→- place explicit actions with `ctx.buy()`, `ctx.sell()`, and `ctx.close_position()`
    48→- manage exits and sizing in code when needed
    49→
    50→This is the best fit for:
    51→
    52→- stateful execution logic
    53→- dynamic stop-loss or take-profit handling
    54→- partial exits, scale-ins, cooldowns, or other runtime rules
    55→- strategies that behave more like trading bots than pure indicators
    56→
    57→### 1.3 The Most Important Separation
    58→
    59→For `IndicatorStrategy`, you usually have **three layers**:
    60→
    61→1. **Indicator layer**: moving averages, RSI, ATR, bands, filters.
    62→2. **Signal layer**: `df['buy']` and `df['sell']`.
    63→3. **Risk defaults layer**: `# @strategy stopLossPct ...`, `takeProfitPct`, `entryPct`, and related defaults.
    64→
    65→Do not mix these into one thing.
    66→
    67→In particular:
    68→
    69→- `buy` / `sell` decide **when the strategy wants to enter or exit**
    70→- `# @strategy` decides **how the engine should size and protect positions by default**
    71→- leverage belongs in product configuration, not in indicator code
    72→
    73→---
    74→
    75→## 2. Which Mode Should You Use?
    76→
    77→| Use Case | Recommended Mode |
    78→|----------|------------------|
    79→| Build indicators, overlays, and signal markers | `IndicatorStrategy` |
    80→| Research entry and exit rules on a dataframe | `IndicatorStrategy` |
    81→| Add fixed stop-loss, take-profit, or entry sizing defaults | `IndicatorStrategy` |
    82→| Need runtime position state and bar-by-bar control | `ScriptStrategy` |
    83→| Need dynamic exits based on current open position | `ScriptStrategy` |
    84→| Need partial close, scale-in/out, or bot-like logic | `ScriptStrategy` |
    85→
    86→Rule of thumb:
    87→
    88→- If your logic can be described as "when condition A happens, buy; when condition B happens, sell", start with `IndicatorStrategy`.
    89→- If your logic sounds like "after entry, keep watching the open position and react differently depending on state", you probably need `ScriptStrategy`.
    90→

    92→
    93→## 3. How To Develop an IndicatorStrategy
    94→
    95→This is the recommended workflow for most new strategy development.
    96→
    97→### 3.1 Step 1: Declare metadata and defaults first
    98→
    99→At the top of the script, define name, description, tunable params, and strategy defaults.
   100→
   101→```python
   102→my_indicator_name = "Trend Pullback Strategy"
   103→my_indicator_description = "Buy pullbacks in an uptrend and exit on weakness."
   104→
   105→# @param fast_len int 20 Fast EMA length
   106→# @param slow_len int 50 Slow EMA length
   107→# @param rsi_len int 14 RSI length
   108→# @param rsi_floor float 45 Minimum RSI for long entries
   109→
   110→# @strategy stopLossPct 0.03
   111→# @strategy takeProfitPct 0.06
   112→# @strategy entryPct 0.25
   113→# @strategy trailingEnabled true
   114→# @strategy trailingStopPct 0.02
   115→# @strategy trailingActivationPct 0.04
   116→# @strategy tradeDirection long
   117→```
   118→
   119→Use `# @param` for values the user may tune often.
   120→
   121→Format:
   122→
   123→```python
   124→# @param <name> <int|float|bool|str|string> <default> <description>
   125→```
   126→
   127→Best practice:
   128→
   129→- read declared params through `params.get(...)`
   130→- `string` is accepted as the same type family as `str`
   131→- if you declare params but hardcode the values instead, the built-in code quality checker will flag it
   132→
   133→Use `# @strategy` for strategy defaults such as:
   134→
   135→- `stopLossPct`: stop-loss ratio, for example `0.03` = 3%
   136→- `takeProfitPct`: take-profit ratio, for example `0.06` = 6%
   137→- `entryPct`: fraction of capital to allocate on entry
   138→- `trailingEnabled`
   139→- `trailingStopPct`
   140→- `trailingActivationPct`
   141→- `tradeDirection`: `long`, `short`, or `both`
   142→
   143→Important:
   144→
   145→- These are **defaults consumed by the engine**.
   146→- They are not extra dataframe columns.
   147→- Do not put `leverage` here.
   148→- Keep the values realistic and confirm them in backtests; the parser is intentionally more permissive than the toy examples shown here.
   149→
   150→### 3.2 Step 2: Copy the dataframe and compute indicators
   151→
   152→Indicator code runs in a sandbox. `pd`, `np`, and a `params` dictionary are already available.
   153→
   154→Recommended baseline:
   155→
   156→```python
   157→df = df.copy()
   158→```
   159→
   160→Expected columns usually include:
   161→
   162→- `open`
   163→- `high`
   164→- `low`
   165→- `close`
   166→- `volume`
   167→
   168→A `time` column may exist, but do not rely on a fixed type.
   169→
   170→Avoid:
   171→
   172→- network access
   173→- file I/O
   174→- subprocesses
   175→- unsafe metaprogramming such as `eval`, `exec`, `open`, or `__import__`
   176→
   177→### 3.3 Step 3: Turn raw conditions into clean `buy` / `sell` signals
   178→
   179→The backtest engine reads **boolean** columns:
   180→
   181→- `df['buy']`
   182→- `df['sell']`
   183→
   184→They should:
   185→
   186→- match the dataframe length exactly
   187→- be boolean after `fillna(False)`
   188→- usually be edge-triggered, unless repeated signals are intentional
   189→
   190→Recommended pattern:
   191→
   192→```python
   193→raw_buy = (ema_fast > ema_slow) & (ema_fast.shift(1) <= ema_slow.shift(1))
   194→raw_sell = (ema_fast < ema_slow) & (ema_fast.shift(1) >= ema_slow.shift(1))
   195→
   196→df['buy'] = (raw_buy.fillna(False) & (~raw_buy.shift(1).fillna(False))).astype(bool)
   197→df['sell'] = (raw_sell.fillna(False) & (~raw_sell.shift(1).fillna(False))).astype(bool)
   198→```
   199→
   200→This keeps your signals from firing on every bar of the same regime.
   201→
   202→### 3.4 Step 4: Decide who owns the exit logic
   203→
   204→This is where stop-loss, take-profit, and position management usually become confusing.
   205→
   206→There are **two valid exit styles** in `IndicatorStrategy`.
   207→
   208→#### Style A: Signal-managed exits
   209→
   210→Your indicator logic itself decides when to exit by setting `df['sell']`.
   211→
   212→Examples:
   213→
   214→- moving-average bearish crossover
   215→- RSI falling below a threshold
   216→- close dropping below an ATR-based stop line
   217→- mean reversion target hit
   218→
   219→Use this style when the exit is part of the strategy idea itself.
   220→
   221→#### Style B: Engine-managed exits
   222→
   223→You let the strategy engine apply fixed defaults declared with `# @strategy`, such as:
   224→
   225→- `stopLossPct`
   226→- `takeProfitPct`
   227→- `entryPct`
   228→- trailing settings
   229→
   230→Use this style when the signal logic should stay simple, and you want the engine to handle fixed protective rules.
   231→
   232→#### Best practice
   233→
   234→Pick one primary owner for exits whenever possible.
   235→
   236→For example:
   237→
   238→- if your edge is "enter on crossover, exit on reverse crossover", keep that in `buy` / `sell`
   239→- if your edge is "enter on signal and let a fixed 3% stop + 6% target manage the trade", use `# @strategy`
   240→
   241→You *can* combine them, but document it clearly so other developers know whether an exit is signal-driven, engine-driven, or both.
   242→
   243→### 3.5 Step 5: Build the `output` object
   244→
   245→Your script must assign a final `output` dictionary:
   246→
   247→```python
   248→output = {
   249→    "name": "My Strategy",
   250→    "plots": [],
   251→    "signals": []
   252→}
   253→```
   254→
   255→Supported keys:
   256→
   257→- `name`
   258→- `plots`
   259→- `signals`
   260→- `calculatedVars` as optional metadata
   261→
   262→Each plot item should contain:
   263→
   264→- `name`
   265→- `data` with length exactly `len(df)`
   266→- `color`
   267→- `overlay`
   268→- optional `type`
   269→
   270→Each signal item should contain:
   271→
   272→- `type`: `buy` or `sell`
   273→- `text`
   274→- `color`
   275→- `data`: list with `None` on bars without a marker
   276→
   277→### 3.6 Step 6: Validate backtest semantics
   278→
   279→Indicator backtests are signal-driven:
   280→
   281→- the engine reads `df['buy']` and `df['sell']`
   282→- signals are treated as bar-close confirmation
   283→- fills are typically on the **next bar open**
   284→
   285→This matters because:
   286→
   287→- an intrabar-looking stop drawn on the current candle is not the same as a next-bar-open fill
   288→- using `shift(-1)` in signal logic introduces look-ahead bias
   289→
   290→Practical nuance:
   291→
   292→- the normalized strategy snapshot can execute with either `next_bar_open` or `same_bar_close`
   293→- most indicator workflows should still be designed with a "confirm on close, usually fill on next open" mental model
   294→- if product settings change the execution timing, rerun the backtest and review fills instead of assuming the semantics stayed the same
   295→

   298→## 4. How To Write Stop-Loss, Take-Profit, and Position Sizing
   299→
   300→This section is the practical answer to the most common implementation question.
   301→
   302→### 4.1 Fixed stop-loss, take-profit, and entry sizing in IndicatorStrategy
   303→
   304→If you want fixed risk defaults, write them as `# @strategy` lines:
   305→
   306→```python
   307→# @strategy stopLossPct 0.03
   308→# @strategy takeProfitPct 0.06
   309→# @strategy entryPct 0.25
   310→# @strategy tradeDirection long
   311→```
   312→
   313→Meaning:
   314→
   315→- `stopLossPct 0.03`: use a 3% stop-loss default
   316→- `takeProfitPct 0.06`: use a 6% take-profit default
   317→- `entryPct 0.25`: allocate 25% of capital on entry
   318→- `tradeDirection long`: long-only by default
   319→
   320→This is the correct choice when you want:
   321→
   322→- simple signal code
   323→- consistent defaults in backtests
   324→- strategy settings that the UI and engine can understand directly
   325→
   326→### 4.2 Indicator-driven exits in IndicatorStrategy
   327→
   328→If your "stop-loss" is actually part of the indicator model, write it as a `sell` signal.
   329→
   330→Example: exit a long when close falls below an ATR-style stop line.
   331→
   332→```python
   333→atr = (df['high'] - df['low']).rolling(14).mean()
   334→stop_line = df['close'].rolling(20).max() - atr * 2.0
   335→
   336→raw_sell = df['close'] < stop_line.shift(1)
   337→df['sell'] = (raw_sell.fillna(False) & (~raw_sell.shift(1).fillna(False))).astype(bool)
   338→```
   339→
   340→In this style:
   341→
   342→- the exit belongs to your indicator logic
   343→- the engine is not inventing the stop for you
   344→- you should explain this in the strategy description or comments
   345→
   346→### 4.3 How position management works in IndicatorStrategy
   347→
   348→For indicator strategies, position management is intentionally simple:
   349→
   350→- use `entryPct` for default entry sizing
   351→- use `tradeDirection` to limit long, short, or both
   352→- use engine-managed stop, take-profit, or trailing defaults if they are fixed
   353→
   354→If you need:
   355→
   356→- scale-in / scale-out
   357→- partial exits
   358→- different logic before and after entry
   359→- stop movement that depends on the current live position state
   360→- cooldowns after a stop
   361→
   362→then the strategy has outgrown `IndicatorStrategy` and should move to `ScriptStrategy`.
   363→

   366→## 5. Full IndicatorStrategy Example
   367→
   368→This example shows a complete developer-oriented pattern: metadata, defaults, indicator calculation, signal generation, and chart output.
   369→
   370→```python
   371→my_indicator_name = "EMA Pullback Strategy"
   372→my_indicator_description = "Buy pullbacks above the slow EMA and exit on trend failure."
   373→
   374→# @param fast_len int 20 Fast EMA length
   375→# @param slow_len int 50 Slow EMA length
   376→# @param rsi_len int 14 RSI length
   377→# @param rsi_floor float 50 Minimum RSI for entry
   378→
   379→# @strategy stopLossPct 0.03
   380→# @strategy takeProfitPct 0.06
   381→# @strategy entryPct 0.25
   382→# @strategy tradeDirection long
   383→
   384→df = df.copy()
   385→
   386→fast_len = int(params.get('fast_len', 20))
   387→slow_len = int(params.get('slow_len', 50))
   388→rsi_len = int(params.get('rsi_len', 14))
   389→rsi_floor = float(params.get('rsi_floor', 50.0))
   390→
   391→ema_fast = df['close'].ewm(span=fast_len, adjust=False).mean()
   392→ema_slow = df['close'].ewm(span=slow_len, adjust=False).mean()
   393→
   394→delta = df['close'].diff()
   395→gain = delta.clip(lower=0).ewm(alpha=1 / rsi_len, adjust=False).mean()
   396→loss = (-delta.clip(upper=0)).ewm(alpha=1 / rsi_len, adjust=False).mean()
   397→rs = gain / loss.replace(0, np.nan)
   398→rsi = 100 - (100 / (1 + rs))
   399→
   400→trend_up = ema_fast > ema_slow
   401→pullback_done = df['close'] > ema_fast
   402→rsi_ok = rsi > rsi_floor
   403→
   404→raw_buy = trend_up & pullback_done & rsi_ok & (~trend_up.shift(1).fillna(False))
   405→raw_sell = (ema_fast < ema_slow) | (rsi < 45)
   406→
   407→buy = (raw_buy.fillna(False) & (~raw_buy.shift(1).fillna(False))).astype(bool)
   408→sell = (raw_sell.fillna(False) & (~raw_sell.shift(1).fillna(False))).astype(bool)
   409→
   410→df['buy'] = buy
   411→df['sell'] = sell
   412→
   413→buy_marks = [df['low'].iloc[i] * 0.995 if buy.iloc[i] else None for i in range(len(df))]
   414→sell_marks = [df['high'].iloc[i] * 1.005 if sell.iloc[i] else None for i in range(len(df))]
   415→
   416→output = {
   417→    "name": my_indicator_name,
   418→    "plots": [
   419→        {
   420→            "name": "EMA Fast",
   421→            "data": ema_fast.fillna(0).tolist(),
   422→            "color": "#1890ff",
   423→            "overlay": True
   424→        },
   425→        {
   426→            "name": "EMA Slow",
   427→            "data": ema_slow.fillna(0).tolist(),
   428→            "color": "#faad14",
   429→            "overlay": True
   430→        },
   431→        {
   432→            "name": "RSI",
   433→            "data": rsi.fillna(0).tolist(),
   434→            "color": "#722ed1",
   435→            "overlay": False
   436→        }
   437→    ],
   438→    "signals": [
   439→        {
   440→            "type": "buy",
   441→            "text": "B",
   442→            "data": buy_marks,
   443→            "color": "#00E676"
   444→        },
   445→        {
   446→            "type": "sell",
   447→            "text": "S",
   448→            "data": sell_marks,
   449→            "color": "#FF5252"
   450→        }
   451→    ]
   452→}
   453→```
   454→
   455→What this example teaches:
   456→
   457→- indicators are computed first
   458→- entries and exits are expressed as boolean signals
   459→- fixed risk defaults are declared separately through `# @strategy`
   460→- chart output is treated as a final rendering step, not mixed into signal logic
   461→
   462→### 5.1 A platform-UI-aligned example
   463→
   464→This version is closer to how developers actually use QuantDinger today:
   465→
   466→- tune common values through `# @param`
   467→- expose default stop / take-profit / entry sizing through `# @strategy`
   468→- set `tradeDirection` explicitly so the saved strategy and backtest panel stay aligned
   469→- keep leverage outside the code and let the product UI own it
   470→
   471→```python
   472→my_indicator_name = "Breakout Retest With Direction Control"
   473→my_indicator_description = "Breakout-and-retest logic with platform-friendly params and default risk settings."
   474→
   475→# @param breakout_len int 20 Breakout lookback bars
   476→# @param retest_buffer float 0.002 Retest tolerance ratio
   477→# @param volume_mult float 1.2 Minimum volume filter
   478→# @param ema_filter_len int 50 Trend filter EMA length
   479→
   480→# @strategy stopLossPct 0.02
   481→# @strategy takeProfitPct 0.05
   482→# @strategy entryPct 0.2
   483→# @strategy trailingEnabled true
   484→# @strategy trailingStopPct 0.015
   485→# @strategy trailingActivationPct 0.03
   486→# @strategy tradeDirection both
   487→
   488→df = df.copy()
   489→
   490→breakout_len = int(params.get('breakout_len', 20))
   491→retest_buffer = float(params.get('retest_buffer', 0.002))
   492→volume_mult = float(params.get('volume_mult', 1.2))
   493→ema_filter_len = int(params.get('ema_filter_len', 50))
   494→
   495→ema_filter = df['close'].ewm(span=ema_filter_len, adjust=False).mean()
   496→range_high = df['high'].rolling(breakout_len).max().shift(1)
   497→range_low = df['low'].rolling(breakout_len).min().shift(1)
   498→volume_avg = df['volume'].rolling(breakout_len).mean()
   499→
   500→long_breakout = df['close'] > range_high
   501→long_retest_ok = df['low'] <= range_high * (1 + retest_buffer)
   502→long_volume_ok = df['volume'] >= volume_avg * volume_mult
   503→long_trend_ok = df['close'] > ema_filter
   504→
   505→short_breakout = df['close'] < range_low
   506→short_retest_ok = df['high'] >= range_low * (1 - retest_buffer)
   507→short_volume_ok = df['volume'] >= volume_avg * volume_mult
   508→short_trend_ok = df['close'] < ema_filter
   509→
   510→raw_buy = long_breakout & long_retest_ok & long_volume_ok & long_trend_ok
   511→raw_sell = short_breakout & short_retest_ok & short_volume_ok & short_trend_ok
   512→
   513→buy = (raw_buy.fillna(False) & (~raw_buy.shift(1).fillna(False))).astype(bool)
   514→sell = (raw_sell.fillna(False) & (~raw_sell.shift(1).fillna(False))).astype(bool)
   515→
   516→df['buy'] = buy
   517→df['sell'] = sell
   518→
   519→buy_marks = [df['low'].iloc[i] * 0.995 if buy.iloc[i] else None for i in range(len(df))]
   520→sell_marks = [df['high'].iloc[i] * 1.005 if sell.iloc[i] else None for i in range(len(df))]
   521→
   522→output = {
   523→    "name": my_indicator_name,
   524→    "plots": [
   525→        {
   526→            "name": "EMA Filter",
   527→            "data": ema_filter.fillna(0).tolist(),
   528→            "color": "#1890ff",
   529→            "overlay": True
   530→        },
   531→        {
   532→            "name": "Range High",
   533→            "data": range_high.fillna(0).tolist(),
   534→            "color": "#52c41a",
   535→            "overlay": True
   536→        },
   537→        {
   538→            "name": "Range Low",
   539→            "data": range_low.fillna(0).tolist(),
   540→            "color": "#f5222d",
   541→            "overlay": True
   542→        }
   543→    ],
   544→    "signals": [
   545→        {
   546→            "type": "buy",
   547→            "text": "L",
   548→            "data": buy_marks,
   549→            "color": "#00E676"
   550→        },
   551→        {
   552→            "type": "sell",
   553→            "text": "S",
   554→            "data": sell_marks,
   555→            "color": "#FF5252"
   556→        }
   557→    ]
   558→}
   559→```
   560→
   561→Why this example maps cleanly to the UI:
   562→
   563→- `# @param` values can be tuned by AI or by manual parameter editing workflows
   564→- `# @strategy` defaults line up with saved strategy defaults and backtest-side risk settings
   565→- `tradeDirection both` makes it obvious that the code is designed for long and short signals
   566→- leverage is still controlled in the product panel instead of being hidden inside source code

   570→## 6. When You Should Switch to ScriptStrategy
   571→
   572→Move to `ScriptStrategy` when the strategy needs runtime state rather than pure dataframe signals.
   573→
   574→Typical triggers:
   575→
   576→- the stop-loss depends on the current open position rather than only on historical series
   577→- you want to adjust stops after entry
   578→- you need partial close or pyramiding
   579→- you want different logic for first entry versus re-entry
   580→- you need cooldown logic, execution throttling, or bot-style workflows
   581→
   582→### 6.1 Required functions
   583→
   584→The safest product-facing contract is:
   585→
   586→- `def on_init(ctx): ...`
   587→- `def on_bar(ctx, bar): ...`
   588→
   589→Why this matters:
   590→
   591→- the runtime compiler strictly requires `on_bar`
   592→- some product-side validation paths still expect both `on_init` and `on_bar`
   593→- to avoid validator/runtime mismatches, define both functions even if `on_init` only initializes state or writes a log line
   594→
   595→### 6.2 Available objects
   596→
   597→`bar` typically exposes:
   598→
   599→- `bar.open`
   600→- `bar.high`
   601→- `bar.low`
   602→- `bar.close`
   603→- `bar.volume`
   604→- `bar.timestamp`
   605→
   606→`ctx` currently exposes:
   607→
   608→- `ctx.param(name, default=None)`
   609→- `ctx.bars(n=1)`
   610→- `ctx.position`
   611→- `ctx.balance`
   612→- `ctx.equity`
   613→- `ctx.log(message)`
   614→- `ctx.buy(price=None, amount=None)`
   615→- `ctx.sell(price=None, amount=None)`
   616→- `ctx.close_position()`
   617→
   618→Notes:
   619→
   620→- `ctx` does not expose the full trading config object directly
   621→- keep leverage, symbol, venue, and credentials in product configuration rather than hardcoding them into the script
   622→- use `ctx.param(...)` for script-level defaults that belong in source code
   623→
   624→`ctx.position` supports both numeric checks and field access patterns such as:
   625→
   626→```python
   627→if not ctx.position:
   628→    ...
   629→
   630→if ctx.position > 0:
   631→    ...
   632→
   633→if ctx.position["side"] == "long":
   634→    ...
   635→```
   636→
   637→### 6.3 Script example with runtime exits
   638→
   639→```python
   640→def on_init(ctx):
   641→    ctx.log("strategy initialized")
   642→
   643→
   644→def on_bar(ctx, bar):
   645→    stop_loss_pct = ctx.param("stop_loss_pct", 0.03)
   646→    take_profit_pct = ctx.param("take_profit_pct", 0.06)
   647→    order_amount = ctx.param("order_amount", 1)
   648→
   649→    bars = ctx.bars(30)
   650→    if len(bars) < 20:
   651→        return
   652→
   653→    closes = [b.close for b in bars]
   654→    ma_fast = sum(closes[-10:]) / 10
   655→    ma_slow = sum(closes[-20:]) / 20
   656→
   657→    if not ctx.position and ma_fast > ma_slow:
   658→        ctx.buy(price=bar.close, amount=order_amount)
   659→        return
   660→
   661→    if not ctx.position:
   662→        return
   663→
   664→    if ctx.position["side"] != "long":
   665→        return
   666→
   667→    entry_price = ctx.position["entry_price"]
   668→
   669→    if bar.close <= entry_price * (1 - stop_loss_pct):
   670→        ctx.close_position()
   671→        return
   672→
   673→    if bar.close >= entry_price * (1 + take_profit_pct):
   674→        ctx.close_position()
   675→        return
   676→
   677→    if ma_fast < ma_slow:
   678→        ctx.close_position()
   679→```
   680→
   681→Use this style when stop-loss and take-profit truly belong to runtime position management instead of pure indicator output.
   682→
   683→Important sizing note:
   684→
   685→- in the current system, saved-strategy backtests still derive position sizing primarily from normalized trading config such as `entryPct`
   686→- treat `amount` in `ctx.buy()` / `ctx.sell()` as runtime order intent, not as the only source of truth for backtest sizing
   687→- always verify actual exposure with a saved-strategy backtest before promoting the script to paper or live trading
   688→
   689→### 6.4 Normal script mode vs bot mode
   690→
   691→Most `ScriptStrategy` workflows run on **closed bars**:
   692→
   693→- the engine evaluates `on_bar(ctx, bar)` after a bar is confirmed
   694→- this is the best mental model for standard strategy backtests and bar-by-bar live execution
   695→
   696→There is also a bot-style runtime mode in the current system:
   697→
   698→- bot mode may feed `on_bar` with synthetic tick-like bars built from the latest price
   699→- this is more suitable for grid, DCA, or other bot-style execution patterns
   700→- if you write code intended for bot mode, test it separately from standard bar-close strategy behavior
   701→
   702→### 6.5 A platform-live-oriented ScriptStrategy example
   703→
   704→This example is closer to how a platform-facing live strategy is usually written:
   705→
   706→- use `ctx.param(...)` for script defaults
   707→- inspect `ctx.position` before deciding whether to open, reverse, reduce, or fully close
   708→- use `ctx.buy()` / `ctx.sell()` for directional intent
   709→- use `ctx.close_position()` when you want an explicit full exit
   710→
   711→```python
   712→def on_init(ctx):
   713→    ctx.log("live strategy initialized")
   714→
   715→
   716→def on_bar(ctx, bar):
   717→    fast_len = int(ctx.param("fast_len", 10))
   718→    slow_len = int(ctx.param("slow_len", 30))
   719→    risk_pct = float(ctx.param("risk_pct", 0.25))
   720→    stop_loss_pct = float(ctx.param("stop_loss_pct", 0.02))
   721→    take_profit_pct = float(ctx.param("take_profit_pct", 0.05))
   722→    allow_short = bool(ctx.param("allow_short", True))
   723→
   724→    bars = ctx.bars(slow_len + 5)
   725→    if len(bars) < slow_len:
   726→        return
   727→
   728→    closes = [b.close for b in bars]
   729→    fast_ma = sum(closes[-fast_len:]) / fast_len
   730→    slow_ma = sum(closes[-slow_len:]) / slow_len
   731→    price = bar.close
   732→
   733→    if not ctx.position:
   734→        if fast_ma > slow_ma:
   735→            ctx.buy(price=price, amount=risk_pct)
   736→            return
   737→        if allow_short and fast_ma < slow_ma:
   738→            ctx.sell(price=price, amount=risk_pct)
   739→            return
   740→        return
   741→
   742→    if ctx.position["side"] == "long":
   743→        entry_price = float(ctx.position["entry_price"])
   744→        if price <= entry_price * (1 - stop_loss_pct):
   745→            ctx.close_position()
   746→            return
   747→        if price >= entry_price * (1 + take_profit_pct):
   748→            ctx.close_position()
   749→            return
   750→        if allow_short and fast_ma < slow_ma:
   751→            ctx.sell(price=price, amount=risk_pct)
   752→            return
   753→
   754→    if ctx.position["side"] == "short":
   755→        entry_price = float(ctx.position["entry_price"])
   756→        if price >= entry_price * (1 + stop_loss_pct):
   757→            ctx.close_position()
   758→            return
   759→        if price <= entry_price * (1 - take_profit_pct):
   760→            ctx.close_position()
   761→            return
   762→        if fast_ma > slow_ma:
   763→            ctx.buy(price=price, amount=risk_pct)
   764→            return
   765→```
   766→
   767→What this example demonstrates:
   768→
   769→- `ctx.param(...)` keeps script defaults visible and editable in source
   770→- `ctx.position` is the switch that separates flat / long / short behavior
   771→- `ctx.buy()` and `ctx.sell()` express directional intent, not just "open long" or "open short" in isolation
   772→- `ctx.close_position()` is the clearest choice when your rule means "exit everything now"
   773→
   774→Backtest vs live differences you should remember:
   775→
   776→- standard script backtests and normal live mode both think in confirmed-bar logic, but bot mode may call the script with synthetic tick-like bars
   777→- `amount` is best treated as runtime order intent; saved-strategy backtests still size mainly from normalized trading config such as `entryPct`
   778→- `ctx.sell()` while long, or `ctx.buy()` while short, may behave like a close-plus-reverse style intent depending on runtime state and product configuration
   779→- if you want a guaranteed full flatten action, prefer `ctx.close_position()` over relying on implicit interpretation
   780→

   783→## 7. Backtesting, Persistence, and Current Limits
   784→
   785→Saved strategies are resolved by the backend into a normalized snapshot for backtesting and execution. Common fields include:
   786→
   787→- `strategy_type`
   788→- `strategy_mode`
   789→- `strategy_code`
   790→- `indicator_config`
   791→- `trading_config`
   792→
   793→Current run types include:
   794→
   795→- `indicator`
   796→- `strategy_indicator`
   797→- `strategy_script`
   798→
   799→Current limitations:
   800→
   801→- cross-sectional strategies are not supported in the current strategy snapshot flow
   802→- `ScriptStrategy` does not support `cross_sectional` live execution mode
   803→- script-strategy backtests do not use the indicator MTF execution path
   804→- strategy backtests expect a valid symbol and non-empty code

   808→## 8. Best Practices
   809→
   810→### 8.1 Avoid look-ahead bias
   811→
   812→- use completed-bar information only
   813→- prefer `shift(1)` for confirmation
   814→- do not use `shift(-1)` in signal logic
   815→
   816→### 8.2 Handle NaNs explicitly
   817→
   818→Rolling and EWM calculations create leading NaNs. Clean them before signal generation.
   819→
   820→### 8.3 Keep all series aligned
   821→
   822→Every `plot['data']` and `signal['data']` list must match `len(df)` exactly.
   823→
   824→### 8.4 Prefer vectorized indicator logic
   825→
   826→For `IndicatorStrategy`, core calculations should be pandas-native whenever possible.
   827→
   828→### 8.5 Keep runtime scripts deterministic
   829→
   830→For `ScriptStrategy`, avoid hidden state outside `ctx`, avoid randomness, and make order intent explicit.
   831→
   832→### 8.6 Put configuration in the right layer
   833→
   834→- use `# @param` and `# @strategy` for indicator defaults
   835→- use `ctx.param()` for script defaults
   836→- keep leverage, signal timing, venue configuration, and credentials outside the strategy code

   840→## 9. Troubleshooting
   841→
   842→### 9.1 `column "strategy_mode" does not exist`
   843→
   844→Your database schema is older than the running code. Apply the required migration on `qd_strategies_trading`.
   845→
   846→### 9.2 `Strategy script must define on_bar(ctx, bar)`
   847→
   848→Your `ScriptStrategy` code is missing the required handler.
   849→
   850→### 9.3 `Missing required functions: on_init, on_bar`
   851→
   852→The current UI verifier expects both functions to exist in the source text.
   853→
   854→### 9.4 `Strategy code is empty and cannot be backtested`
   855→
   856→The saved strategy does not contain valid code for the selected mode.
   857→
   858→### 9.5 Marker or plot length mismatch
   859→
   860→All chart output arrays must align exactly with the dataframe length.
   861→
   862→### 9.6 Strategy behaves strangely in backtest
   863→
   864→Check these first:
   865→
   866→- did you accidentally use future data?
   867→- are your `buy` / `sell` signals edge-triggered?
   868→- are you mixing signal-driven exits with engine-driven exits without documenting it?
   869→- are your `# @strategy` defaults aligned with the strategy idea?
   870→
   871→### 9.7 Backend logs
   872→
   873→If strategy creation, verification, backtest, or execution fails, check backend logs first. Common issue classes:
   874→
   875→- schema mismatch
   876→- invalid JSON or config payloads
   877→- code verification failure
   878→- market or symbol mismatch
   879→- credential or exchange configuration issues

   883→## 10. Full Workflow: Indicator IDE -> Saved Strategy -> Live Trading
   884→
   885→This is the most practical product workflow for most teams.
   886→
   887→### 10.1 Prototype in Indicator IDE
   888→
   889→Start in the Indicator IDE when you are still shaping the idea:
   890→
   891→1. Write indicator logic on `df`.
   892→2. Declare tunable inputs with `# @param`.
   893→3. Declare default risk settings with `# @strategy`.
   894→4. Add chart-friendly `plots` and `signals`.
   895→5. Run indicator-side backtests until the signal density and fills make sense.
   896→
   897→At this stage, the goal is not to perfect live execution. The goal is to make the logic visible, testable, and easy to iterate.
   898→
   899→### 10.2 Tune and validate in the product
   900→
   901→Once the indicator behaves correctly:
   902→
   903→1. Use the code quality checker to catch missing metadata or suspicious patterns.
   904→2. Run backtests with realistic symbol, timeframe, commission, slippage, and leverage settings.
   905→3. If needed, use AI tuning or structured tuning to compare parameter combinations.
   906→4. Apply tuned values back into the code so the source remains the single visible truth.
   907→
   908→Recommended mindset:
   909→
   910→- let the code describe the signal logic
   911→- let `# @param` and `# @strategy` describe tunable defaults
   912→- let the panel own market, leverage, date range, and execution environment
   913→
   914→### 10.3 Save the indicator as a strategy
   915→
   916→Once the signal model is stable:
   917→
   918→1. Save the current indicator code.
   919→2. Create or save a strategy record from the product flow.
   920→3. Confirm that the saved strategy snapshot has the expected mode, defaults, and trading config.
   921→4. Run strategy backtests from the persisted record, not only from the raw editor state.
   922→
   923→Why this matters:
   924→
   925→- saved-strategy backtests are closer to the real execution path
   926→- normalized snapshots may apply execution timing and trading-config defaults differently from the raw editor view
   927→- this is the right place to catch symbol, mode, config, and persistence mismatches
   928→
   929→### 10.4 Decide whether IndicatorStrategy is enough
   930→
   931→Stay with `IndicatorStrategy` if:
   932→
   933→- entries and exits are mainly signal-based
   934→- fixed stop-loss / take-profit / trailing defaults are enough
   935→- you do not need position-state-dependent runtime logic
   936→
   937→Promote to `ScriptStrategy` if:
   938→
   939→- the open position must be monitored bar by bar
   940→- exits depend on current position state rather than only on historical series
   941→- you need cooldowns, partial exits, scale-ins, or bot-like runtime behavior
   942→
   943→### 10.5 Move to paper or live trading carefully
   944→
   945→Before enabling live trading:
   946→
   947→1. Verify exchange, broker, symbol, and credential configuration.
   948→2. Recheck execution timing assumptions.
   949→3. Confirm that leverage, direction, and sizing live in the right product configuration layer.
   950→4. Start with conservative sizing and narrow symbol scope.
   951→5. Review runtime logs and actual order behavior before scaling up.
   952→
   953→Live trading should be treated as a separate validation stage, not as a continuation of editor-only experimentation.
   954→

   957→## 11. Common Mistakes vs Correct Patterns
   958→
   959→This section highlights the mistakes that most often cause misleading backtests, confusing strategy behavior, or product/runtime mismatches.
   960→
   961→### 11.1 Declaring `# @param` but never reading it
   962→
   963→Wrong:
   964→
   965→```python
   966→# @param fast_len int 20 Fast EMA length
   967→
   968→df = df.copy()
   969→fast_len = 20
   970→ema_fast = df['close'].ewm(span=fast_len, adjust=False).mean()
   971→```
   972→
   973→Correct:
   974→
   975→```python
   976→# @param fast_len int 20 Fast EMA length
   977→
   978→df = df.copy()
   979→fast_len = int(params.get('fast_len', 20))
   980→ema_fast = df['close'].ewm(span=fast_len, adjust=False).mean()
   981→```
   982→
   983→Why:
   984→
   985→- declaring a param tells the product and AI tuning flow that the value is intended to be adjustable
   986→- if the code never reads `params.get(...)`, the declaration becomes cosmetic and the quality checker may warn
   987→
   988→### 11.2 Making `buy` / `sell` fire on every bar
   989→
   990→Wrong:
   991→
   992→```python
   993→df['buy'] = df['close'] > ema_fast
   994→df['sell'] = df['close'] < ema_fast
   995→```
   996→
   997→Correct:
   998→
   999→```python
  1000→raw_buy = df['close'] > ema_fast
  1001→raw_sell = df['close'] < ema_fast
  1002→
  1003→df['buy'] = (raw_buy.fillna(False) & (~raw_buy.shift(1).fillna(False))).astype(bool)
  1004→df['sell'] = (raw_sell.fillna(False) & (~raw_sell.shift(1).fillna(False))).astype(bool)
  1005→```
  1006→
  1007→Why:
  1008→
  1009→- repeated signals on every bar can distort entries, exits, and chart markers
  1010→- edge-triggered signals are usually closer to the intended strategy semantics
  1011→
  1012→### 11.3 Writing leverage into the strategy source
  1013→
  1014→Wrong:
  1015→
  1016→```python
  1017→# @strategy leverage 10
  1018→```
  1019→
  1020→Correct:
  1021→
  1022→```python
  1023→# @strategy entryPct 0.2
  1024→# @strategy stopLossPct 0.02
  1025→# @strategy takeProfitPct 0.05
  1026→```
  1027→
  1028→Then set leverage in the product panel or saved-strategy trading configuration.
  1029→
  1030→Why:
  1031→
  1032→- leverage belongs to execution configuration, not indicator metadata
  1033→- hiding leverage in code makes backtests harder to read and easier to misconfigure
  1034→
  1035→### 11.4 Using `shift(-1)` and accidentally introducing look-ahead bias
  1036→
  1037→Wrong:
  1038→
  1039→```python
  1040→df['buy'] = (df['close'].shift(-1) > ema_fast).fillna(False)
  1041→```
  1042→
  1043→Correct:
  1044→
  1045→```python
  1046→raw_buy = df['close'] > ema_fast
  1047→df['buy'] = (raw_buy.fillna(False) & (~raw_buy.shift(1).fillna(False))).astype(bool)
  1048→```
  1049→
  1050→Why:
  1051→
  1052→- `shift(-1)` reaches into future data
  1053→- strategies that look amazing with future leakage usually collapse in real execution
  1054→
  1055→### 11.5 Treating `ctx.buy(..., amount=...)` as absolute backtest size
  1056→
  1057→Wrong mental model:
  1058→
  1059→```python
  1060→ctx.buy(price=bar.close, amount=1.0)
  1061→```
  1062→
  1063→"This guarantees the backtest always uses exactly 100% of capital."
  1064→
  1065→Correct mental model:
  1066→
  1067→```python
  1068→position_pct = float(ctx.param("risk_pct", 0.25))
  1069→ctx.buy(price=bar.close, amount=position_pct)
  1070→```
  1071→
  1072→And then verify the saved-strategy backtest using the normalized trading config.
  1073→
  1074→Why:
  1075→
  1076→- in the current system, saved-strategy backtests still derive sizing mainly from normalized config such as `entryPct`
  1077→- `amount` is best treated as runtime order intent, not as the only source of truth for historical sizing
  1078→
  1079→### 11.6 Using `ctx.sell()` or `ctx.buy()` when you really mean "fully flatten now"
  1080→
  1081→Risky:
  1082→
  1083→```python
  1084→if stop_hit:
  1085→    ctx.sell(price=bar.close, amount=0.25)
  1086→```
  1087→
  1088→Clearer:
  1089→
  1090→```python
  1091→if stop_hit:
  1092→    ctx.close_position()
  1093→```
  1094→
  1095→Why:
  1096→
  1097→- `ctx.buy()` / `ctx.sell()` express directional intent and may be interpreted through current position state
  1098→- if your rule means "exit everything now", `ctx.close_position()` is the least ambiguous choice
  1099→
  1100→### 11.7 Mixing signal exits and engine exits without documenting it
  1101→
  1102→Risky:
  1103→
  1104→```python
  1105→# @strategy stopLossPct 0.02
  1106→# @strategy takeProfitPct 0.05
  1107→
  1108→df['sell'] = some_other_exit_condition
  1109→```
  1110→
  1111→Better:
  1112→
  1113→```python
  1114→# Primary exit: reverse signal
  1115→# Secondary protection: engine-managed fixed stop-loss / take-profit
  1116→# @strategy stopLossPct 0.02
  1117→# @strategy takeProfitPct 0.05
  1118→
  1119→df['sell'] = reverse_signal
  1120→```
  1121→
  1122→Why:
  1123→
  1124→- the combination itself may be valid
  1125→- the real problem is when nobody knows which exit path is supposed to dominate
  1126→

  1226→| `name` | recommended | Display name |
  1227→| `plots` | recommended | Chart series output |
  1228→| `signals` | recommended | Buy/sell marker output |
  1229→| `calculatedVars` | optional | Extra metadata or computed values |

  1231→Each `plot` item commonly contains:
  1232→

  1248→| `data` | List aligned to `len(df)`, using `None` where no marker exists |
  1249→
  1250→### 12.6 Fast reminders
  1251→
  1252→- `df['buy']` and `df['sell']` should be boolean and length-aligned
  1253→- prefer edge-triggered signals
  1254→- avoid `shift(-1)` in signal logic
  1255→- prefer `ctx.close_position()` when the rule clearly means "exit everything now"
  1256→- treat `amount` as runtime order intent, then verify sizing with saved-strategy backtests

  1260→## 13. Recommended Development Workflow
  1261→
  1262→1. Prototype the idea as an `IndicatorStrategy`.
  1263→2. Validate plots, signal density, and next-bar-open backtest behavior.
  1264→3. Add clear `# @param` and `# @strategy` metadata.
  1265→4. Decide explicitly whether exits are signal-managed or engine-managed.
  1266→5. Save the strategy and run strategy backtests from the persisted record.
  1267→6. Promote to `ScriptStrategy` only when you truly need runtime position logic.
  1268→7. Move to paper or live trading only after configuration, credentials, and market semantics are verified.
