01
نظرة عامة على قاعدة البيانات (Database Overview)

تعتمد منظومة فيكسور على Supabase كمنصة قاعدة بيانات رئيسية، وهي بنية مبنية فوق PostgreSQL — أقوى أنظمة قواعد البيانات العلائقية مفتوحة المصدر. تُدار قاعدة البيانات عبر Supabase Cloud مما يوفر طبقة API مدمجة (PostgREST)، نظام مصادقة مدمج (Auth)، واشتراكات في الوقت الحقيقي (Realtime Subscriptions). يتم التفاعل مع قاعدة البيانات من جانب العميل عبر supabase-js، ومن جانب الخادم عبر @supabase/ssr مع دعم Server-Side Rendering.

تتكون قاعدة بيانات فيكسور من 27 جدولاً رئيسياً مُقسّمة إلى سبع مجالات وظيفية: جداول التداول الخمسة (analyses، trades، daily_signals، signal_tracking، price_alerts)، وجداول المستخدم الستة (profiles، user_settings، user_strategies، user_streaks، moxi_personas، user_memories)، وجداول النقاط والاشتراكات (credit_points، points_balances، points_transactions، point_packs، premium_plans، premium_subscriptions، payments)، وجداول الذكاء الاصطناعي الستة (copilot_conversations، copilot_messages، domain_events، vixor_decisions، agent_audit_log، agent_jobs، agent_tokens)، بالإضافة إلى جداول المراقبة والتجارب والنظام.

02
جداول التداول (Trading Tables)

تشكل جداول التداول القلب النابض لمنظومة فيكسور، حيث تُخزّن جميع البيانات المتعلقة بتحليلات السوق والصفقات والإشارات والتنبيهات السعرية. تم تصميم هذه الجداول لتدعم دورة حياة كاملة للتداول بدءاً من التحليل التقني مروراً بإنشاء الإشارة وحتى تنفيذ الصفقة وتتبعها. كل جدول يخدم مرحلة محددة في هذه الدورة ويرتبط بالجداول الأخرى عبر مفاتيح أجنبية تضمن سلامة البيانات.

جدول التحليلات — analyses

الجدول الأكبر والأكثر تعقيداً في المنظومة. يخزن كل تحليل تقني يتم إجراؤه عبر الذكاء الاصطناعي أو يدوياً. يحتوي على 25 حقلاً تشمل التوصية (recommendation) من نوع recommendation_type، مستوى الثقة (confidence)، نقاط الدخول والخروج (entry، stop_loss، take_profit[])، والهيكل السعري (market_structure) ككائن JSON. يمر كل تحليل عبر أربع مراحل: queued ← processing ← complete | failed.

جدول الصفقات — trades

يسجّل كل صفقة فعلية ينفذها المستخدم مع جميع تفاصيلها: الاتجاه (direction: long | short)، الحالة (status: open | closed | cancelled)، أسعار الدخول والخروج، الكمية، الربح والخسارة (pnl، pnl_pips)، ونسبة المخاطرة للعائد (r_multiple). يمكن ربط كل صفقة بتحليل محدد عبر analysis_id ومرتبطة بالمستخدم عبر user_id.

جدول الإشارات اليومية — daily_signals

جدول عام (Global) يحتوي على إشارات التداول اليومية لجميع أزواج العملات. لا يرتبط بمستخدم محدد بل يُولَّد بواسطة النظام centrally. يحتوي على زوج العملات، الإطار الزمني، التوصية، الثقة، ونقاط الدخول والخروج مع منطاطق السيولة والهيكل السعري. يتم تتبع كل إشارة عبر signal_tracking.

جدول تتبع الإشارات — signal_tracking

يربط الإشارات اليومية بالمستخدمين ويتتبع أداء كل إشارة. الحالة تتبع نوع signal_status: pending → active → tp1_hit/tp2_hit/tp3_hit/sl_hit/expired/cancelled. يحتوي على بيانات حركة السعر (current_price، previous_price)، والانحراف الأقصى للأداء (max_favorable_excursion، max_adverse_excursion)، وعدد نقاط الأرباح المُحققة (hit_tp).

جدول التنبيهات السعرية — price_alerts

يسمح للمستخدمين بإنشاء تنبيهات على أسعار محددة مع شروط مختلفة: above (أعلى من)، below (أدنى من)، crosses_up (يتجاوز صعوداً)، crosses_down (يتجاوز هبوطاً). كل تنبيه مرتبط بالمستخدم ويحتوي على حالة (active، triggered، cancelled) وتاريخ التفعيل.

الجدول عدد الأعمدة المفتاح الأساسي المفاتيح الأجنبية الوصف
analyses 25 id user_id → profiles تحليلات الذكاء الاصطناعي
trades 19 id user_id، analysis_id سجل الصفقات المنفذة
daily_signals 16 id بدون إشارات يومية عامة
signal_tracking 18 id user_id، signal_id تتبع أداء الإشارات
price_alerts 11 id user_id → profiles تنبيهات الأسعار
03
جداول المستخدم (User Tables)

تدير جداول المستخدم البيانات الشخصية والتخصيصية لكل مستخدم مسجّل في المنظومة. تتبع فيكسور نهج Profile Table Pattern حيث يتم تخزين البيانات الأساسية في جدول profiles المرتبط مباشرة بنظام المصادقة Supabase Auth عبر auth.users. باقي الجداول تمدّد هذه البنية لتشمل الإعدادات والاستراتيجيات والسلاسل والذاكرة والشخصيات.

جدول الملفات الشخصية — profiles

الجدول المركزي للمستخدم يحتوي على 13 حقلاً: المعرّف (id) الذي يطابق auth.uid()، اسم العرض (display_name)، اسم المستخدم (username)، رابط الصورة الرمزية (avatar_url)، كود الإحالة (referral_code) المُولَّد عبر الدالة gen_referral_code()، المُحيل (referred_by)، وأيام السلسلة (streak_days) بالإضافة إلى تكامل Telegram (telegram_id، telegram_username، telegram_photo_url). يحتوي على مفتاح أجنبي ذاتي (referred_by → profiles.id) لتمثيل شجرة الإحالات.

جدول الإعدادات — user_settings

علاقة واحد لواحد (1:1) مع المستخدم. يحتوي على إعدادات التطبيق المتقدمة: قنوات الإشعارات (notification_channels) كـ JSON، مزوّد LLM المفضل (preferred_llm_provider)، مفاتيح API (llm_api_keys) المشفرة كـ JSON، بيانات البورصة (exchange_credentials)، وإعدادات Telegram وWebhook. لا يمكن أن يكون للمستخدم أكثر من سجل إعدادات واحد.

جدول الاستراتيجيات — user_strategies

يسمح لكل مستخدم بتعريف استراتيجيات تداول متعددة. كل استراتيجية تحتوي على: اسم الاستراتيجية، أزواج العملات المستهدفة (pairs[])، نمط التداول (trading_style)، تحمل المخاطر (risk_tolerance)، والأطر الزمنية المفضلة (preferred_timeframes[]). يمكن تفعيل استراتيجية واحدة فقط في كل لحظة عبر is_active.

جدول السلاسل — user_streaks

يتتبع سلسلة الأيام المتتالية التي يستخدم فيها المستخدم التطبيق. يحتوي على السلسلة الحالية (current_streak)، أطول سلسلة (longest_streak)، وتاريخ آخر يوم مكتمل (last_completed_date). يُستخدم في نظام التحفيز ومكافأة النقاط عند تحقيق سلاسل يومية.

جدول الشخصيات — moxi_personas

جزء من منظومة MOXI (Modular Orchestrated eXchange Intelligence). يخزن الشخصيات المخصصة التي يمكن للمستخدم اختيارها أو تدريبها. كل شخصية تمثل أسلوب تحليل وتواصل مختلف (مثلاً: المحلل التقني المحافظ، المتداول العدواني، مدرب المخاطر). تؤثر الشخصية على طريقة توليد التحليلات والتفاعل عبر Copilot.

جدول الذاكرة — user_memories

نظام الذاكرة الدائم في PostgreSQL الذي يُمكّن فيكسور من "تذكّر" تفضيلات المستخدم وأنماط سلوكه وأخطاءه ورؤاه واستراتيجياته. كل ذكرى تحتوي على فئة (category): preference، behavior، mistake، insight، strategy، محتوى النص (content)، وبيانات وصفية (metadata). يُستخدم بواسطة MemoryStore لتخصيص تجربة المستخدم بشكل مستمر.

⚠️ خصوصية الذاكرة
بيانات الذاكرة حساسة لأنها تعكس أنماط سلوك المستخدم. يجب تطبيق سياسات RLS صارمة لضمان عدم وصول أي مستخدم لذاكرة مستخدم آخر. يتم إنشاء الذاكرة تلقائياً من التفاعلات ولا يمكن للمستخدم حذفها مباشرة.
04
جداول المحفظة والنقاط (Wallet & Points Tables)

تُشكّل جداول النقاط والاشتراكات منظومة اقتصادية متكاملة داخل فيكسور تسمح بإدارة الائتمانات والمشتريات والاشتراكات المميزة. تم تصميم هذه المنظومة وفق نمط Double-Entry Accounting المبسّط، حيث يتم تسجيل كل عملية في جدول المعاملات مع تحديث الرصيد تلقائياً عبر الدوال المخزّنة.

جدول أرصدة النقاط — points_balances

علاقة واحد لواحد مع المستخدم (المفتاح الأساسي هو user_id). يحتوي على رصيد النقاط الحالي (balance)، وإجمالي النقاط المكتسبة مدى الحياة (lifetime_earned)، وتاريخ آخر تحديث. تُعدَّل هذه القيم حصرياً عبر الدوال المخزّنة credit_points() وspend_points() لضمان اتساق البيانات ومنع التعديل المباشر.

جدول معاملات النقاط — points_transactions

سجل دائم لكل حركة نقاط (Credit/Debit). كل معاملة تحتوي على: المبلغ (delta) يمكن أن يكون سالباً أو موجباً، السبب (reason) من تعداد points_reason (8 أسباب: signup_bonus، analysis_cost، pack_purchase، referral_bonus، daily_streak، premium_grant، admin_adjust، telegram_stars_purchase)، وبيانات وصفية (metadata). يوفر هذا الجدول تتبعاً كاملاً لكل نقطة دخلت أو خرجت من حساب المستخدم.

جدول حزم النقاط — point_packs

تعريف الحزم المتاحة للشراء. يحتوي على: اسم الحزمة، عدد النقاط (points)، نقاط المكافأة الإضافية (bonus_points)، السعر بالسنتات (price_cents)، وشارة العرض (badge). يتم التحكم بالعرض عبر is_active وsort_order. لا يرتبط هذا الجدول بمستخدم محدد بل هو بيانات مرجعية عامة.

جدول خطط Premium — premium_plans

مشابه لجدول الحزم لكنه يُعرّف خطط الاشتراك المميزة. يحتوي على: اسم الخطة، الميزات (features) كـ JSON، فترة الاشتراك (interval)، السعر، وشارة العرض. تتحكم القيمة is_active بإظهار الخطة للمستخدمين.

جدول الاشتراكات — premium_subscriptions

يسجّل اشتراكات المستخدمين الفعلية في خطط Premium. يحتوي على: حالة الاشتراك (status)، تاريخ انتهاء الفترة الحالية (current_period_end)، والمفتاح الأجنبي plan_id المرتبط بـ premium_plans. يسمح لكل مستخدم باشتراك نشط واحد فقط.

جدول المدفوعات — payments

سجل شامل لكل عملية شراء سواء كانت حزم نقاط أو اشتراكات مميزة. يدعم الدفع عبر Telegram Stars (telegram_charge_id، amount_stars) وأنظمة أخرى. كل دفعة تحتوي على حمولة (payload)، حالة (status)، تاريخ التأكيد (confirmed_at)، ومراجع للخطة أو الحزمة المشتراة عبر plan_id وpack_id.

الجدول العلاقة بالمستخدم المفاتيح الأجنبية الوظيفة
points_balances 1:1 المفتاح = user_id رصيد النقاط الحالي

05
جداول الذكاء الاصطناعي (AI Tables)

تُمثّل جداول الذكاء الاصطناعي البنية التحتية لجميع قدرات فيكسور الذكية، من مساعد Copilot التفاعلي إلى نظام اتخاذ القرارات عبر الوكلاء (Agents). تتعامل هذه الجداول مع المحادثات والرسائل والأحداثDomain والقرارات والعمليات المدققة. التصميم يفصل بين بيانات المحادثة وبيانات العمليات لضمان الأداء والقابلية للتوسع.

جدول محادثات Copilot — copilot_conversations

يمثّل كل محادثة بين المستخدم ونظام Copilot. يحتوي على: عنوان المحادثة (title)، معرّف الوكيل (agent_id) إذا كانت المحادثة متخصصة، وعلم الإجماع (is_consensus) الذي يشير إلى ما إذا كانت النتيجة مبنية على توافق عدة وكلاء. كل محادثة مرتبطة بمستخدم واحد عبر user_id.

جدول رسائل Copilot — copilot_messages

يخزن كل رسالة (سؤال أو إجابة) ضمن محادثة. يحتوي على: الدور (role: user/assistant/system)، المحتوى (content)، معرّف الوكيل الذي أجاب (agent_id)، وبيانات وصفية (metadata). مرتبط بـ copilot_conversations عبر conversation_id. يسمح هذا التصميم بمحادثات متعددة مع وكلاء مختلفين ضمن نفس المحادثة.

جدول أحداث المجال — domain_events

سجل أحداث مجال النظام (Domain Event Log). يُستخدم من طرف VixorEvents لتسجيل الأحداث الهامة مثل: إنشاء تحليل، تنفيذ صفقة، إشعار مستخدم. يحتوي على: نوع الحدث (event_type)، حمولة البيانات (payload) كـ JSON، ويعتمد حقل user_id الاختياري لربط الحدث بمستخدم محدد. يدعم Supabase Realtime للاشتراك في الأحداث الجديدة فورياً.

جدول قرارات فيكسور — vixor_decisions

يسجّل كل قرار يتخذه نظام الذكاء الاصطناعي مع سياقه الكامل. يحتوي على: نوع القرار (decision_type)، العنوان (title)، الوصف التفصيلي (description)، بيانات القرار (data)، مستوى الثقة (confidence)، وملاحظات المستخدم (feedback). يدعم أيضاً بيانات العملات الرقمية (token_symbol، chain، workspace، severity) لقرارات التداول.

جدول سجل تدقيق الوكلاء — agent_audit_log

سجل أمني شامل لكل طلب يُنفذه وكيل (Agent). يسجّل: المسار (route)، الطريقة (method)، حالة الاستجابة (status)، ومدة التنفيذ بالمللي ثانية (duration_ms). يُستخدم للمراجعة الأمنية واكتشاف الأنماط المشبوهة وتحليل أداء الوكلاء.

جدول عمليات الوكلاء — agent_jobs

يتتبع العمليات غير المتزامنة التي ينفذها الوكلاء. كل عملية تحتوي على: الحالة (status)، نسبة التقدم (progress)، النتيجة (result) كـ JSON، ورسالة الخطأ إن وجدت. مرتبط بالمستخدم والرمز المميز عبر user_id وtoken_id.

جدول رموز الوكلاء — agent_tokens

يدير رموز المصادقة (API Tokens) التي يستخدمها الوكلاء للوصول إلى المنظومة. كل رمز يحتوي على: تجميع SHA (token_hash)، نطاقات الصلاحيات (scopes[])، اسم وصفياً، تاريخ انتهاء الصلاحية (expires_at)، وآخر استخدام. هذا يضمن وصول الوكلاء الخارجيين بأسلوب OAuth2 مبسط.

06
جداول المراقبة (Watching Tables)

تخدم جداول المراقبة وظيفة تتبع الأزواج المفضلة وإدارة ملاحظات التداول. تتيح هذه الجداول للمستخدمين تنظيم أسواقهم المفضلة، تصنيف الأزواج حسب استراتيجياتهم، وتدوين الملاحظات التي تربط بين التحليل والتنفيذ. التصميم يدعم قوائم مراقبة متعددة لكل مستخدم مع ترتيب مخصص.

جدول قوائم المراقبة — watchlists

يمكن لكل مستخدم إنشاء قوائم مراقبة متعددة لتنظيم أزواج العملات. يحتوي على: اسم القائمة (name)، علم القائمة الافتراضية (is_default) الذي يحدد ما إذا كانت هذه هي القائمة التي تظهر عند فتح التطبيق، وترتيب العرض (sort_order). عند إنشاء حساب جديد، يُنشأ تلقائياً قائمة مراقبة افتراضية واحدة. مرتبط بجدول profiles عبر user_id.

جدول عناصر المراقبة — watchlist_items

يخزن كل زوج عملات ضمن قائمة مراقبة محددة. يحتوي على: زوج العملات (pair)، التصنيف (category) الذي يمكن أن يكون مثل "Major" أو "Crypto" أو "Exotic"، ملاحظات مخصصة (notes)، وترتيب العرض (sort_order). مرتبط بـ watchlists عبر watchlist_id. يمكن لنفس الزوج أن يظهر في قوائم مراقبة متعددة لنفس المستخدم أو لمستخدمين مختلفين.

جدول ملاحظات التداول — trading_notes

جداول التجارب (Experiment Tables)

تُمكّن جداول التجارب منظومة فيكسور من تنفيذ تجارب خوارزمية للتحسين المستمر لاستراتيجيات التداول. هذه الجداول تنتمي لمكون P2-ENGINES (محرك التجارب) وتدعم نمط Generational Optimization حيث تُقيَّم كل جيل من الحلول وتُحسَّن عبر الخوارزميات الجينية. التصميم يفصل بين إعدادات التجربة وتوليداته لضمان المرونة وسهولة التحليل.

جدول التجارب — experiments

يمثّل كل تجربة مستقلة يُنفذها المستخدم أو النظام تلقائياً. يحتوي على: إعدادات التجربة (config) ككائن JSON يحتوي على المعلمات الخوارزمية والقيود، نتيجة التجربة النهائية (result) كـ JSON، الحالة (status): running | completed | failed، تاريخ البدء والانتهاء. مرتبط بالمستخدم عبر user_id. يمكن للمستخدم إجراء تجارب متعددة بالتوازي.

جدول توليدات التجربة — experiment_generations

يخزن بيانات كل جيل (Generation) ضمن التجربة. في الخوارزميات الجينية، كل جيل يمثل مجموعة من الحلول المُقيَّمة. يحتوي على: رقم الجيل (generation)، أفضل نتيجة (best_score)، متوسط النتائج (avg_score)، والمجموعة الكاملة من الحلول (population). مرتبط بـ experiments عبر experiment_id. هذا الجدول يسمح برسم منحنى التحسين عبر الأجيال وتحليل تقارب الخوارزمية.

✅ مرونة التصميم
استخدام JSON لتخزين config وresult وpopulation يُمكّن من دعم أنواع مختلفة من التجارب دون تعديل مخطط قاعدة البيانات. يمكن إضافة معلمات جديدة أو تغيير بنية الحلول بمرونة كاملة.
-- مثال: هيكل تجربة خوارزمية جينية { "config": { "algorithm": "genetic", "population_size": 100, "mutation_rate": 0.05, "crossover_rate": 0.8, "max_generations": 50, "fitness_function": "sharpe_ratio", "constraints": { "max_risk": 0.02 } }, "result": { "best_solution": { "params": {...}, "sharpe": 2.1 }, "total_generations": 42, "convergence": true } }

جداول النظام (System Tables)

جدول الإشعارات — notifications

كل إشعار يحتوي على: عنوان (title)، نص المحتوى (body)، نوع الإشعار (type) مثل "signal" أو "trade" أو "system"، حالة القراءة مع تاريخ القراءة (read_at). الحقول الممتدة تشمل: قناة الإرسال (channel)، حمولة البيانات (payload) كـ JSON، حالة الإرسال (status: pending | sent | failed)، وتاريخ الإرسال الفعلي (sent_at) مع رسالة الخطأ إن فشل.

دورة حياة الإشعار

العلاقات (Relations)

تعتمد قاعدة بيانات فيكسور على نظام علاقات مرتبط عبر المفاتيح الأجنبية (Foreign Keys) التي تربط الجداول ببعضها لضمان سلامة البيانات Referential Integrity. تُدار العلاقات عبر Supabase وتُعكَس تلقائياً في أنواع TypeScript المُولّدة. فهم هذه العلاقات أساسي لتصميم الاستعلامات الفعالة وتحليل البيانات عبر الجداول المتعددة.

العلاقة المركزية — profiles ↔ جميع الجداول

جدول profiles هو المركز الذي تتفرع منه جميع البيانات. ما يقارب 15 جدولاً تحتوي على user_id كمفتاح أجنبي مرتبط بـ profiles.id. هذا يخلق علاقة واحد لعدة (1:N) من الملف الشخصي إلى كل جدول فرعي. التصميم يضمن حذف البيانات الآمن عبر CASCADE DELETE عند حذف حساب مستخدم.

العلاقات المرجعية (Lookup)
  • الاشتراكات: premium_subscriptions → premium_plans (عدة لواحد — عدة اشتراكات تشير لنفس الخطة)
  • المدفوعات: payments → point_packs و payments → premium_plans (عدة لواحد)
العلاقة الذاتية

جدول profiles يحتوي على علاقة ذاتية حيث يشير referred_by إلى profiles.id في نفس الجدول. هذا يمثّل شجرة إحالات متعددة المستويات حيث يمكن للمستخدم "أ" أن يشير إلى المستخدم "ب" الذي أشار إليه المستخدم "ج". يجب الحذر من التعمق العودي عند الاستعلام عن هذه الشجرة.

الفهارس (Indexes)

الفهارس (Indexes) هي العنصر الأهم لتحسين أداء الاستعلامات في PostgreSQL. بدون فهارس مناسبة، يضطر محرك قاعدة البيانات إلى إجراء مسح كامل للجدول (Sequential Scan) مما يُبطئ الاستعلامات بشكل كبير مع نمو حجم البيانات. في فيكسور، معظم الاستعلامات تُفلترة حسب user_id بسبب سياسات RLS، مما يجعل فهارس هذا العمود الأولوية القصوى.

فهارس المستخدم (Critical — الأولوية القصوى)

بما أن سياسات RLS تُضيف شرط WHERE user_id = auth.uid() تلقائياً لكل استعلام، فإن جميع الجداول التي تحتوي على user_id تحتاج فهرساً على هذا العمود. بدون هذا الفهرس، سيُحوّل كل استعلام بسيط إلى مسح كامل للجدول. يُنصح باستخدام فهارس BRIN للجداول الكبيرة المرتبة زمنياً وB-tree للباقي.

القيود (Constraints)

القيود (Constraints) في PostgreSQL تُنفّذ قواعد البيانات على مستوى المخطط لضمان صحة واتساق البيانات. تمنع القيود إدراج بيانات غير صالحة أو غير متسقة وتضمن سلامة البيانات حتى في حالة وجود أخطاء برمجية في طبقة التطبيق. في فيكسور، تُستخدم أربعة أنواع رئيسية من القيود: NOT NULL، UNIQUE، CHECK، وFOREIGN KEY.

قيود NOT NULL

تضمن أن حقولاً محددة لا يمكن أن تحتوي على قيم فارغة. في فيكسور، الحقول التالية إلزامية: user_id في جميع الجداول المرتبطة بالمستخدم، status في جداول الحالة مثل analyses وsignal_tracking وtrades، pair في جداول التداول، content في copilot_messages وuser_memories، recommendation في analyses (يمكن أن يكون NULL في حالة الفشل)، وdelta وreason في points_transactions.

قيود UNIQUE

تضمن عدم تكرار القيم. في فيكسور: profiles.referral_code يجب أن يكون فريداً عالمياً، user_settings.user_id يضمن إعداداً واحداً لكل مستخدم (علاقة 1:1)، points_balances.user_id يضمن رصيداً واحداً لكل مستخدم. كود الإحالة يُولَّد عبر الدالة gen_referral_code() التي تضمن التفرد عبر التحقق من عدم وجود الكود مسبقاً.

قيود CHECK

تُنفّذ قواعد التحقق على مستوى القيم. التعدادات (ENUM) تُمثّل أحد أشكال قيود CHECK. في فيكسور: recommendation_type يقتصر على BUY | SELL | WAIT، analysis_status يقتصر على queued | processing | complete | failed، signal_status يقتصر على 8 حالات محددة، points_reason يقتصر على 8 أسباب محددة. يمكن إضافة قيود CHECK إضافية مثل: confidence >= 0 AND confidence <= 100، balance >= 0 في points_balances.

قيود FOREIGN KEY

تضمن سلامة العلاقات بين الجداول. جميع المفاتيح الأجنبية في فيكسور تستخدم ON DELETE CASCADE أو ON DELETE SET NULL حسب السياق. CASCADE يُستخدم عندما يجب حذف البيانات الفرعية مع البيانات الرئيسية (مثل حذف قائمة مراقبة يحذف عناصرها)، وSET NULL يُستخدم عندما يجب الاحتفاظ بالبيانات مع إزالة المرجع (مثل حذف تحليل لا يحذف الصفقات المرتبطة به).

✅ مبدأ الدفاع في العمق
القيود على مستوى قاعدة البيانات هي خط الدفاع الأخير. حتى لو كانت طبقة التطبيق تحتوي على تحقق كامل، تظل القيود ضرورية لحماية البيانات من: أخطاء البرمجة، استعلامات مباشرة، وحالات التزامن المتزامن (Race Conditions).

المشغلات (Triggers)

المشغلات (Triggers) في PostgreSQL هي إجراءات تُنفّذ تلقائياً عند حدوث أحداث محددة على جدول (INSERT، UPDATE، DELETE). تُستخدم في فيكسور لإدارة القيم الافتراضية، تسجيل التغييرات، وتنفيذ منطق العمل على مستوى قاعدة البيانات. تصميم المشغلات بعناية يُقلل من التعقيد في طبقة التطبيق ويضمن تنفيذ المنطق بشكل متسق.

مشغلات الطوابع الزمنية (Auto-Timestamps)

جميع الجداول في فيكسور تحتوي على created_at وupdated_at. يُعيّن created_at تلقائياً عبر قيمة افتراضية now() عند الإدراج، بينما يُحدّث updated_at تلقائياً عبر مشغّل BEFORE UPDATE. هذا يضمن دقة الطوابع الزمنية دون اعتماد على طبقة التطبيق.

مشغلات حذف متتالي (CASCADE Deletes)

عند حذف ملف شخصي (Profile)، تُحذف تلقائياً جميع البيانات المرتبطة عبر المفاتيح الأجنبية مع ON DELETE CASCADE. هذا يشمل: التحليلات، الصفقات، الإشعارات، المحادثات، الإعدادات، الاستراتيجيات، السلاسل، وكل البيانات الفرعية. يجب الحذر عند تنفيذ هذا لأن الحذف لا يمكن التراجع عنه (Hard Delete).

مشغلات توليد كود الإحالة

عند إنشاء ملف شخصي جديد، يُنشأ كود إحالة فريد تلقائياً عبر الدالة gen_referral_code(). يمكن تنفيذ هذا عبر مشغّل BEFORE INSERT على جدول profiles يُولّد الكود إذا لم يتم توفيره. الدالة تُنتج كوداً عشوائياً وتتحقق من عدم وجوده في الجدول قبل الإدراج.

مشغلات مخصصة مقترحة
  • تحديث السلسلة: مشغّل AFTER UPDATE على user_streaks يُرسل إشعاراً عند تجاوز سلسلة جديدة أطول سلسلة سابقة
  • تنبيهات الأسعار: مشغّل يعمل بشكل دوري عبر pg_cron لفحص price_alerts النشطة ومقارنتها بالأسعار الحالية
  • انتهاء الإشارات: مشغّل يُحدّث حالة الإشارات المنتهية الصلاحية من active إلى expired
  • تنظيف الإشعارات: مشغّل مجدول عبر pg_cron يحذف الإشعارات المقروءة الأقدم من 30 يوماً
  • تنظيف سجل التدقيق: مشغّل يحذف سجلات agent_audit_log الأقدم من 90 يوماً
-- مثال: مشغّل تحديث الطابع الزمني CREATE OR REPLACE FUNCTION update_updated_at() RETURNS TRIGGER AS $$ BEGIN NEW.updated_at = now(); RETURN NEW; END; $$ LANGUAGE plpgsql; CREATE TRIGGER set_updated_at BEFORE UPDATE ON analyses FOR EACH ROW EXECUTE FUNCTION update_updated_at();

طرق العرض (Views)

طرق العرض (Views) في PostgreSQL توفر طبقة تجريد فوق الجداول الأساسية، تسمح بتبسيط الاستعلامات المعقدة، تحسين الأداء عبر تجميع البيانات مسبقاً، وتوفير واجهات مُعاد تسميتها لواجهة برمجة التطبيقات. في فيكسور، تُستخدم طرق العرض المقترحة لتقديم رؤى جاهزة وملخصات دون الحاجة إلى استعلامات معقدة في كل مرة.

عرض إحصائيات المستخدم — user_stats

طريقة عرض تجمّع بيانات المستخدم من عدة جداول في صف واحد. تحتوي على: إجمالي الصفقات، معدل الربح (Win Rate)، إجمالي R-Multiple، متوسط الثقة في التحليلات، رصيد النقاط، طول السلسلة الحالية، وعدد الملاحظات. يُبسّط طلبات لوحة التحكم (Dashboard) التي تحتاج بيانات من عدة جداول.

عرض أداء الإشارات — signal_performance

تربط بين daily_signals وsignal_tracking لحساب أداء كل إشارة: نسبة النجاح، متوسط R-Multiple، عدد مرات ضرب كل TP. يُستخدم في تقارير الأداء وفي صفحة الإحصائيات لمساعدة المستخدمين على تقييم جودة الإشارات.

عرض المحفظة — user_wallet_summary

تدمج بين points_balances، premium_subscriptions، وآخر معاملة من points_transactions لتقديم نظرة شاملة على المحفظة: الرصيد الحالي، حالة الاشتراك، وتاريخ آخر عملية.

عرض سجل النشاط — user_activity_feed

تُوحّد الأحداث من عدة جداول (analyses، trades، signal_tracking، trading_notes، copilot_conversations) في سجل نشاط واحد مرتب زمنياً. كل سجل يحتوي على: نوع النشاط، الوصف، التاريخ، والبيانات المرتبطة.

عرض التحليلات النشطة — active_analyses

تعرض التحليلات المكتملة (status = 'complete') التي لم تنتهِ صلاحيتها بعد مع إرفاق بيانات التتبع من signal_tracking إذا وُجدت. تُستخدم في لوحة التحكم الرئيسية لعرض التحليلات الحالية ذات الصلة.

-- مثال: طريقة عرض إحصائيات المستخدم CREATE VIEW user_stats AS SELECT p.id AS user_id, p.display_name, (SELECT COUNT(*) FROM trades t WHERE t.user_id = p.id) AS total_trades, (SELECT COUNT(*) FROM trades t WHERE t.user_id = p.id AND t.pnl > 0)::float / NULLIF((SELECT COUNT(*) FROM trades t WHERE t.user_id = p.id), 0) AS win_rate, pb.balance AS points_balance, pb.lifetime_earned AS points_earned, us.current_streak, us.longest_streak, (SELECT COUNT(*) FROM analyses a WHERE a.user_id = p.id) AS total_analyses FROM profiles p LEFT JOIN points_balances pb ON pb.user_id = p.id LEFT JOIN user_streaks us ON us.user_id = p.id;

الدوال (Functions)

الدوال المخزّنة (Stored Functions) في PostgreSQL تُنفّذ منطق العمل على مستوى قاعدة البيانات مما يُحسّن الأداء ويضمن تنفيذ العمليات بشكل ذري (Atomic). في فيكسور، تُستخدم الدوال لإدارة النقاط، توليد الأكواد، وتنفيذ عمليات مالية تتطلب اتساقاً صارماً. التعامل مع النقاط يتم حصرياً عبر الدوال المخزّنة لمنع أي تعديل مباشر للأرصدة.

دالة توليد كود الإحالة — gen_referral_code()

تُولّد كود إحالة فريد من 8 أحرف. تعمل بدون معلمات وتُرجع سلسلة نصية. الخوارزمية تولّد كوداً عشوائياً من أحرف وأرقام وتتحقق من عدم وجوده في profiles.referral_code. إذا وُجد الكود (احتمال ضئيل جداً)، تُعيد التوليد. تُستخدم تلقائياً عند إنشاء ملف شخصي جديد.

دالة إضافة النقاط — credit_points()

تضيف نقاطاً لحساب المستخدم بشكل ذري. المعلمات: _user (UUID)، _amount (number)، _reason (points_reason)، _meta (JSON اختياري). تقوم بثلاث عمليات في معاملة واحدة: التحقق من وجود الرصيد، إضافة المبلغ إلى balance وlifetime_earned في points_balances، وتسجيل المعاملة في points_transactions. تُرجع الرصيد الجديد.

دالة صرف النقاط — spend_points()

تخصم نقاطاً من حساب المستخدم مع التحقق من sufficiency. المعلمات مماثلة لـ credit_points() لكن _amount يجب أن يكون موجباً. تقوم بـ: التحقق من كفاية الرصيد، طرح المبلغ من balance، وتسجيل المعاملة. إذا كان الرصيد غير كافٍ، تُرجع خطأ يمنع العملية بالكامل.

دوال مقترحة
  • transfer_points(): نقل نقاط بين مستخدمين (للإحالات أو الهدايا) مع التحقق من الكفاية وتسجيل المعاملتين
  • get_user_stats(): إرجاع ملخص شامل لبيانات المستخدم من عدة جداول في استدعاء واحد
  • expire_old_alerts(): تعيين حالة التنبيهات المنتهية إلى expired بشكل مجمع
  • cleanup_old_data(): حذف البيانات القديمة مع حفظ إحصائيات مجملة
  • recalculate_streak(): إعادة حساب سلسلة المستخدم عند تغير التاريخ
⚠️ قاعدة أساسية للنقاط
يُمنع منعًا باتًا تعديل points_balances.balance مباشرة عبر UPDATE. جميع عمليات النقاط يجب أن تمر عبر credit_points() أو spend_points() فقط. هذا يضمن تسجيل كل عملية في points_transactions ويمنع التناقضات المالية.

سياسات الأمان (RLS Policies)

Row Level Security (RLS) هو آلية أمان في PostgreSQL تُقيّد الوصول على مستوى الصفوف (Rows) وليس الجداول فقط. في فيكسور، تُفعّل RLS على جميع الجداول بحيث لا يستطيع أي مستخدم الوصول إلا إلى بياناته الخاصة. تُضاف سياسة افتراضية ترفض كل الوصول (DENY ALL) عند تفعيل RLS، ثم تُضاف سياسات محددة للسماح بالعمليات المطلوبة.

نمط السياسات في فيكسور

تتبع فيكسور نمط User-Isolation Policy حيث كل سياسة تحتوي على شرط auth.uid() = user_id. هذا يعني أن Supabase يُضيف تلقائياً هذا الشرط لكل استعلام يأتي من العميل. على سبيل المثال، عندما يطلب المستخدم جميع تحليلاته، يتحول الاستعلام تلقائياً إلى: SELECT * FROM analyses WHERE user_id = 'user-uuid'.

وسيط المصادقة — requireSupabaseAuth

نظام المصادقة في فيكسور يعمل عبر وسيط (Middleware) يُنفّذ قبل كل دالة الخادم. الوسيط يستخرج رمز Bearer Token من رأس الطلب (Authorization Header)، ثم يُنشئ عميلين لـ Supabase: عميل التحقق باستخدام Service Role Key للتحقق من صلاحية الرمز مع auth.getUser(token)، وعميل المستخدم باستخدام User JWT الذي يُفعّل RLS تلقائياً. إذا فشل التحقق، يُرجع الوسيط خطأ 401 Unauthorized.

أنواع السياسات المُطبّقة
نوع العملية السياسة الوصف
SELECT قراءة البيانات الخاصة المستخدم يقرأ صفوفه فقط
INSERT إدراج بيانات مرتبطة المستخدم يُدرج بـ user_id = auth.uid()
UPDATE تحديث البيانات الخاصة المستخدم يُعدّل صفوفه فقط
DELETE حذف البيانات الخاصة المستخدم يحذف صفوفه فقط
استثناءات RLS

بعض الجداول تحتاج استثناءات: daily_signals هو جدول عام (Global) يمكن لأي مستخدم قراءته لأن الإشارات ليست خاصة بمستخدم محدد. point_packs وpremium_plans هما جداول مرجعية عامة. domain_events يمكن قراءته من قبل أي مستخدم مصادق عليه. لهذه الجداول، تُستخدم سياسات SELECT USING (true) للسماح بالقراءة العامة مع الحفاظ على RLS للعمليات الأخرى.

🔴 تحذير أمني بالغ الأهمية
لا تستخدم أبداً مفتاح الخدمة (Service Role Key) في العميل (Browser). مفتاح الخدمة يتجاوز RLS تماماً ويمنح صلاحية كاملة على جميع البيانات. استخدمه فقط في جانب الخادم (Server Functions) مع الوسيط requireSupabaseAuth. في العميل، استخدم دائماً getSupabaseOrThrow() الذي يُرجع عميلاً بـ JWT المستخدم.
-- مثال: سياسة RLS نموذجية ALTER TABLE analyses ENABLE ROW LEVEL SECURITY; CREATE POLICY "users_read_own_analyses" ON analyses FOR SELECT USING (auth.uid() = user_id); CREATE POLICY "users_insert_own_analyses" ON analyses FOR INSERT WITH CHECK (auth.uid() = user_id); CREATE POLICY "users_update_own_analyses" ON analyses FOR UPDATE USING (auth.uid() = user_id) WITH CHECK (auth.uid() = user_id); CREATE POLICY "users_delete_own_analyses" ON analyses FOR DELETE USING (auth.uid() = user_id); -- استثناء: قراءة عامة للإشارات ALTER TABLE daily_signals ENABLE ROW LEVEL SECURITY; CREATE POLICY "authenticated_read" ON daily_signals FOR SELECT USING (auth.role() = 'authenticated');

التحسين (Optimization)

تحسين أداء قاعدة البيانات هو عملية مستمرة تتطلب مراقبة وتعديلاً دورياً. في فيكسور، مع نمو عدد المستخدمين وحجم البيانات، يصبح التحسين ضرورياً للحفاظ على سرعة الاستجابة. يتضمن التحسين عدة محاور: تحسين الاستعلامات، إدارة الاتصالات، تجميع البيانات، والتخزين المؤقت.

تحسين الاستعلامات (Query Optimization)
  • استخدام SELECT محدد: تجنب SELECT * وحدد الأعمدة المطلوبة فقط لتقليل حجم البيانات المنقولة
  • الترقيم (Pagination): استخدم .range(0, 19) أو .limit(20) لتحميل البيانات على دفعات
  • الفلاتر المبكرة: طبّق فلاتر .eq('status', 'active') قبل الترتيب للاستفادة من الفهارس
  • تفادي JOINs غير ضرورية: استخدم الاستعلامات المباشرة بدلاً من JOINs المعقدة عند الإمكان
  • EXPLAIN ANALYZE: راجع خطة التنفيذ للاستعلامات البطيئة عبر لوحة تحكم Supabase
إدارة الاتصالات (Connection Pooling)

Supabase يوفر Connection Pooling عبر PgBouncer الذي يدير مجموعة اتصالات مشتركة. في فيكسور، يُستخدم وضع Transaction Mode عبر Port 6543 لعميل الخادم، حيث يُعطَى كل معاملة اتصالاً من المجموعة. للعميل (Browser)، يُستخدم وضع Session Mode عبر Port 5432. هذا يُقلل عدد الاتصالات الفعلية إلى PostgreSQL ويمنع استنزاف الموارد.

التخزين المؤقت (Caching)

تُستخدم استراتيجيات تخزين مؤقت متعددة في فيكسور: Supabase Cache مدمج مع الاستعلامات (30 ثانية افتراضياً)، Browser Cache عبر TanStack Query مع تحديد staleTime وgcTime، وLocal Memory Cache على الخادم للبيانات المرجعية مثل premium_plans وpoint_packs التي نادراً ما تتغير. البيانات التي لا تتغير أبداً (جداول مرجعية) تُخزّن مؤقتاً لمدة طويلة، بينما البيانات الديناميكية (الأسعار، الإشعارات) تُخزّن مؤقتاً لفترات قصيرة أو تُستخدم مع Realtime Subscriptions للتحديثات الفورية.

الاشتراكات في الوقت الحقيقي

بدلاً من الاستقصاء الدوري (Polling)، تُستخدم Supabase Realtime للاستماع للتغييرات على الجداول المحددة. هذا يُقلل الحمل على قاعدة البيانات ويوفر تحديثات فورية. تُستخدم Realtime بشكل أساسي لـ: analyses (لإشعار المستخدم عند اكتمال تحليل)، notifications (للإشعارات الجديدة)، وsignal_tracking (لتتبع تحديثات الإشارات).

⚠️ مراقبة الأداء
راقب مؤشرات الأداء عبر لوحة تحكم Supabase بانتظام: عدد الاتصالات النشطة، أطول الاستعلامات (Slow Queries)، استهلاك التخزين، ومعدل القراءة/الكتابة. إذا تجاوز وقت الاستعلام 100 مللي ثانية، فهو مرشح للتحسين.

معايير التسمية (Naming Standards)

معايير التسمية (Naming Conventions) في قاعدة بيانات فيكسور تتبع نظاماً صارماً ومتسقاً يُسهّل فهم المخطط والتعاون بين المطوّرين. الاختيار المتسق للأسماء يُقلل من الأخطاء البرمجية ويجعل قاعدة البيانات أكثر قابلية للصيانة والتوسع. تتبع فيكسور معايير PostgreSQL و Supabase الموصى بها.

أسماء الجداول (Table Names)
  • الصيغة: جمع باللغة الإنجليزية، أحرف صغيرة فقط، مفصولة بشرطة سفلية (snake_case)
  • أمثلة: analyses، daily_signals، user_strategies، copilot_conversations
  • البادئات: user_ للجداول المرتبطة بالمستخدم، agent_ لجداول الوكلاء
  • التركيب: عند وجود علاقة، يُسمّى الجدول الفرعي باسم مركب مثل watchlist_items (عناصر قائمة المراقبة)
أسماء الأعمدة (Column Names)
  • الصيغة: snake_case، أحرف صغيرة، وصفية ودقيقة
  • المفاتيح الأساسية: id (UUID مُولّد عبر gen_random_uuid())
  • المفاتيح الأجنبية: {table}_id مثل user_id، analysis_id، watchlist_id
  • الطوابع الزمنية: created_at، updated_at، {event}_at مثل sent_at، triggered_at
  • الأعلام (Booleans): is_{adjective} مثل is_active، is_default، is_pinned
  • المصفوفات: جمع بالإنجليزية مع أقواس مثل tags[]، take_profit[]، scopes[]
أسماء التعدادات (Enum Names)
  • الصيغة: {entity}_{attribute} بالـ snake_case
  • أمثلة: recommendation_type، analysis_status، signal_status، points_reason
  • القيم: أحرف صغيرة أو UPPER_CASE حسب السياق (مثل BUY|SELL|WAIT)
أسماء الدوال والمشغلات
  • الدوال: فعل_اسم مثل gen_referral_code، credit_points، spend_points
  • المشغلات: {action}_{table} مثل set_updated_at
  • سياسات RLS: {operation}_{subject}_{object} مثل users_read_own_analyses

قواعد الترحيل (Migration Rules)

الترحيل (Migrations) في فيكسور تُدار عبر Supabase Migrations وهي مجموعة من ملفات SQL المُرقّمة تسريعاً تُنفّذ بالتتابع لتعديل مخطط قاعدة البيانات. كل ترحيل يمثّل تغييراً واحداً أو مجموعة تغييرات مترابطة على المخطط. إدارة الترحيل بشكل صحيح ضرورية لضمان تطابق المخطط عبر جميع البيئات (Development، Staging، Production).

صيغة أسماء الترحيلات

تتبع فيكسور صيغة {timestamp}_{description}.sql حيث الطابع الزمني هو رقم يونيكس (مثال: 20260612000000_add_domain_events.sql). الترقيم يضمن التنفيذ بالترتيب الصحيح. الوصف يجب أن يكون مختصراً وواضحاً بالإنجليزية ويصف التغيير الرئيسي.

قواعد الترحيل الإلزامية
  • إضافة فقط (Additive Only): يُفضّل إضافة أعمدة وجداول جديدة فقط دون حذف أو تعديل أعمدة موجودة لتقليل مخاطر فقدان البيانات
  • NO DROP: يُمنع حذف أعمدة أو جداول في بيئة الإنتاج إلا بعد مرور فترة احتفاظ كافية (Deprecation Period)
  • إعادة توليد الأنواع: بعد كل ترحيل، شغّل supabase gen types لتحديث src/shared/supabase/types.ts
  • التراجع (Rollback): كل ترحيل يجب أن يكون قابلاً للتراجع. اكتب ملف .sql عكسي للتراجع عند الحاجة
  • الاختبار: اختبر كل ترحيل على نسخة من قاعدة البيانات الإنتاجية قبل التطبيق الفعلي
  • التوثيق: أضف تعليقاً في أعلى كل ملف ترحيل يشرح الغرض والتأثير
ترتيب عمليات الترحيل
  1. إنشاء ملف الترحيل الجديد عبر supabase migration new {description}
  2. كتابة SQL للتعديلات مع التزامن مع المخطط الحالي
  3. اختبار الملف محلياً عبر supabase db reset
  4. تشغيل supabase gen types لتحديث أنواع TypeScript
  5. مراجعة التغييرات على الأنواع وتحديث الكود المتأثر
  6. تطبيق الترحيل على بيئة Staging للاختبار
  7. النشر إلى الإنتاج عبر supabase db push
  8. التحقق من سلامة البيانات بعد الترحيل
تعامل مع البيانات الحساسة

عند إضافة أعمدة جديدة حساسة (مثل مفاتيح API أو بيانات شخصية)، يجب: استخدام تشفير at-rest عبر Supabase Vault أو التشفير التطبيقي، عدم تضمين البيانات الحساسة في نوع TypeScript المُولّد إذا أمكن، وإضافة سياسات RLS فورية لمنع الوصول غير المصرح به.

🔴 تحذير الإنتاج
لا تُطبّق ترحيلات تحتوي على DROP TABLE أو DROP COLUMN أو ALTER TYPE مباشرة على بيئة الإنتاج. هذه العمليات قد تؤدي إلى فقدان بيانات أو توقف الخدمة. استخدم دائماً نهج Additive Migrations مع مرحلة إهمال (Deprecation) كافية.

استراتيجية النسخ الاحتياطي (Backup Strategy)

استراتيجية النسخ الاحتياطي في فيكسور تعتمد بشكل أساسي على ميزات Supabase Cloud المدمجة مع إجراءات إضافية لتعزيز الحماية. النسخ الاحتياطي ليس خياراً بل ضرورة حتمية لحماية بيانات المستخدمين وضمان استمرارية الخدمة. تتبع فيكسور نموذج 3-2-1 للنسخ الاحتياطي: ثلاث نسخ، على وسيطين مختلفين، مع نسخة واحدة خارج الموقع.

نسخ Supabase الاحتياطية المدمجة

يوفر Supabase Cloud نسخاً احتياطية تلقائية يومية لقاعدة البيانات مع الاحتفاظ بـ 7 أيام من النسخ في الخطة المجانية و30 يوماً في الخطة المدفوعة. يتم تخزين النسخ على Amazon S3 مع تشفير AES-256. يمكن استعادة قاعدة البيانات بالكامل إلى أي نقطة زمنية خلال فترة الاحتفاظ عبر لوحة تحكم Supabase أو عبر API.

الاستعادة لنقطة زمنية (Point-in-Time Recovery — PITR)

ميزة PITR في Supabase تسمح باستعادة قاعدة البيانات إلى أي لحظة محددة خلال آخر 7 أيام (أو أكثر حسب الخطة). هذا ضروري في حالات: حذف بيانات بالخطأ، تنفيذ ترحيل معيب، أو اختراق أمني. يتم الاستعادة عبر تحديد التاريخ والوقت المستهدف وينشئ Supabase نسخة جديدة من قاعدة البيانات عند تلك النقطة. العملية تستغرق عادة من دقائق إلى ساعات حسب حجم البيانات.

النسخ الاحتياطي التطبيقي (Application-Level Backups)
  • تصدير دوري: تصدير بيانات الجداول المرجعية (premium_plans، point_packs) أسبوعياً بصيغة JSON
  • نسخ الإعدادات: الاحتفاظ بنسخة من مخطط قاعدة البيانات (schema.sql) في المستودع مع كل ترحيل
  • نسخ البيانات الحساسة: تصدير بيانات user_memories وmoxi_personas بشكل منفصل لحمايتها
  • مراقبة النسخ: إعداد تنبيهات عند فشل أي عملية نسخ احتياطي
