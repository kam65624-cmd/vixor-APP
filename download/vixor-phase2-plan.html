الفصل الاول
الملخص التنفيذي
يتضمن هذا التقرير خطة تنفيذية مفصلة لتطوير اربع ميزات جوهرية في تطبيق VIXOR، وهو رفيق الصفقة (Trade Companion) الذي يعمل كتطبيق ويب داخل تليجرام. التطبيق مبني على TanStack Start مع React 19 وSupabase وVite وموزع على Vercel. يحتوي المشروع حاليا على 363 ملف TypeScript و16 نطاق عمل (DDD) و92 مكتبة وقت التشغيل و33+ صفحة واجهة مستخدم تعمل بالكامل.
بناء على تحليل شامل للمشروعين VIXOR الحالي ومشروع QuantDinger المفتوح المصدر، تبين ان VIXOR يمتلك بالفعل معظم البنية التحتية المطلوبة. المحرك التحليلي (SMC/ICT) يعمل بالكامل بنظام حتمي بدون مفاتيح API خارجية. نظام الاشارات يتم توليده بشكل دوري ويخزن في قاعدة البيانات. اتصال Binance WebSocket موجود ويعمل للاسعار الحية. نظام الاشعارات يدعم تليجرام والبريد والتطبيق نفسه.
النتيجة الرئيسية: لا نحتاج لبناء انظمة من الصفر. نحتاج لربط الانظمة الموجودة ببعضها وتحسين نقاط الضعف المحددة. QuantDinger يserve كمرجع تصميمي وليس كمصدر كود مباشر لانه مكتوب بـ Python وVIXOR يعمل بـ TypeScript في بيئة Serverless.
الميزات الاربع المطلوبة وتقييم حالتها الحالية هي كالتالي: اولا، ربط محرك التحليل بالواجهة وهو يعمل فعلا لكن زر المشاركة في صفحة النتائج وهمي بدون وظيفة. ثانيا، دورة حياة الاشارات من pending الى tp_hit/sl_hit وهذا غير موجود تماما. ثالثا، محرك المشاركة على X وTelegram وهذا غير موجود. رابعا، مراقبة الاسعار الحية والفحص الحالي يعتمد على Cron وليس لحظيا.
الفصل الثاني
الحالة الحالية - ما يعمل وما لا يعمل
بعد مراجعة كل ملف في المشروع (استخدام ادوات فحص تلقائية + قراءة يدوية للملفات الحرجة)، الحالة الحالية كالتالي. هذا الفصل يركز فقط على الانظمة المرتبطة بالميزات الاربع المطلوبة وليس قائمة شاملة لكل شيء في المشروع.
محرك التحليل المحلي (SMC/ICT) - يعمل
الملف الرئيسي: src/domains/analysis/engine/engine.ts (1115 سطر). خط الانابيب: بنية السوق ← مفاهيم SMC (Order Blocks, FVGs, مناطق سيولة, BOS/CHOCH) ← انماط الشموع (74 نمط) ← تشكيلات بيانية (20 تشكيل) ← انماط هارمونيك (8 انماط) ← مؤشرات فنية (RSI, MACD, BB, EMA, ADX) ← حساب المخاطرة والعرض. النظام حتمي بالكامل ولا يحتاج اي مفاتيح API خارجية.
نظام الاشارات (daily_signals) - جزئي
جدول daily_signals في Supabase يخزن: pair, timeframe, recommendation, confidence, entry, stop_loss, take_profit[], reasons[], pattern. يتم التوليد عبر Cron في server/api/generate-signals.ts. المشكلة: لا يوجد حقل status ولا دورة حياة (lifecycle). الاشارة تُولد وتُنسى - لا يتم تتبعها حتى تصل للـ TP او SL.
زر المشاركة - معطل
في صفحة src/routes/_authenticated/analysis.$id.tsx السطر 1956، زر المشاركة (Share2) موجود كايقونة فقط بدون اي معالج onClick. الكود لا يحتوي على navigator.share ولا اي منطق مشاركة حقيقي. الزر وهمي تماما.
اتصال Binance WebSocket - يعمل
src/shared/market-data/binance-ws.ts (276 سطر) وsrc/shared/market-data/use-live-prices.ts (183 سطر). الـ Singleton BinanceWS يعمل على جانب العميل (client-side) ويحصل على اسعار لحظية بدون API key. يُستخدم في الـ Dashboard لكنه غير موصل بنظام الاشارات لمراقبة مستويات TP/SL.
فاحص التنبيهات (Alert Checker) - جزئي
src/domains/trading/server/alert-checker.ts (237 سطر). يعمل عبر Cron (ليس لحظيا). يفحص شروط above/below/crosses_up/crosses_down ويرسل اشعارات. يعمل بشكل صحيح لكنه بطيء لان الـ Cron يعمل كل دقائق وليس كل ثانية.
نظام الاشعارات - يعمل
src/shared/notifications/ يحتوي على قنوات: telegram.ts, email.ts, in-app.ts, webhook.ts. الاشعارات تعمل فعلا عبر الـ notificationRouter. عند بناء نظام Signal Lifecycle، يمكن استخدامه مباشرة لارسال اشعارات TP hit / SL hit.
الفصل الثالث
تحليل مشروع QuantDinger المفتوح المصدر
مشروع QuantDinger (github.com/crazymonkey-1470/QuantDinger) هو منصة تحليل كمي كاملة مكتوبة بـ Python/Flask مع PostgreSQL وRedis. يغطي اسواق العملات المشفرة والاسهم الامريكية والصينية والفوركس والسلع عبر 12+ بورصة. هذا الفصل يحدد ما يمكن الاستفادة منه فعلا في VIXOR وما لا ينفع.
ملاحظة مهمة: QuantDinger مكتوب بـ Python (Flask + pandas + numpy). VIXOR مكتوب بـ TypeScript (TanStack Start + React) ويعمل على Vercel Serverless. لا يمكن نسخ كود Python مباشرة. ما نستفيد منه هو المفاهيم والتصميم وليس الكود نفسه.
ما ينفع من QuantDinger (مفاهيم وتصميم فقط): اولا، صيغة الـ prompt المهيكلة للتحليل بالذكاء الاصطناعي - نمط JSON المُخرج يحتوي على trendOutlook, supportResistance, entrySuggestion, exitSuggestion. ثانيا، مفهوم Signal Lifecycle - الاشارات تمر بحالات محددة وليست مجرد نقطة بيانات. ثالثا، نمط Data Source Factory - كل مصدر بيانات يتبع واجهة موحدة مع نظام fallback متعدد المستويات. رابعا، انماط المؤشرات الفنية الاضافية مثل Pivot Points وVolume Ratio وRange Position.
ما لا ينفع: مكتبة المؤشرات الفنية (pandas/numpy) لا يمكن نقلها مباشرة لكن VIXOR لديه بالفعل RSI, MACD, BB, EMA, ADX, ATR وهي المؤشرات الاساسية. نظام الـ Backtest في QuantDinger اكثر تطورا (trailing stop, multi-timeframe) لكن VIXOR لديه محرك Backtest يعمل بالفعل. نظام التداول المباشر (Live Trading) على 15 بورصة لا ينفع لان VIXOR رفيق تحليل وليس منصة تداول.
الميزة الاولى
دورة حياة الاشارات (Signal Lifecycle)
هذه هي الميزة الاهم. حاليا جدول daily_signals يخزن الاشارات كنقاط بيانات ساكنة بدون اي تتبع. الهدف هو تحويل كل اشارة الى كيان حي يُراقب من لحظة الدخول حتى الوصول للهدف او وقف الخسارة.
التصميم المستوحى من QuantDinger: في QuantDinger، كل اشارة تمر بدورة حياة واضحة. يوجد جدول pending_orders تُكتب فيه الاشارات الجديدة، ثم PendingOrderWorker يفحصها ويُنفذها. عند التنفيذ، يتحول حالتها. هذا النمط هو ما سنطبقه في VIXOR ولكن بلغة TypeScript ومتوافق مع Serverless.
الخطوة 1: انشاء جدول signal_tracking في Supabase
CREATE TYPE signal_status AS ENUM ( 'pending', -- تم توليد الاشارة، لم تُراقب بعد 'active', -- يُراقب السعر حاليا 'tp1_hit', -- الهدف الاول تحقق 'tp2_hit', -- الهدف الثاني تحقق (كل الاهداف) 'sl_hit', -- وقف الخسارة تحقق 'expired', -- انتهت صلاحية الاشارة 'cancelled' -- الغاها المستخدم ); CREATE TABLE signal_tracking ( id UUID PRIMARY KEY DEFAULT gen_random_uuid(), user_id UUID NOT NULL REFERENCES profiles(id) ON DELETE CASCADE, signal_id UUID REFERENCES daily_signals(id), source_type TEXT NOT NULL DEFAULT 'daily_signal', -- بيانات الاشارة pair TEXT NOT NULL, direction TEXT NOT NULL, -- 'BUY' or 'SELL' entry_price DOUBLE PRECISION, stop_loss DOUBLE PRECISION, take_profit JSONB, -- [tp1, tp2, ...] -- حالة التتبع status signal_status NOT NULL DEFAULT 'pending', current_price DOUBLE PRECISION, previous_price DOUBLE PRECISION, max_favorable DOUBLE PRECISION DEFAULT 0, max_adverse DOUBLE PRECISION DEFAULT 0, hit_tp INTEGER, -- كم هدف تحقق (0, 1, 2) -- توقيت activated_at TIMESTAMPTZ, resolved_at TIMESTAMPTZ, expires_at TIMESTAMPTZ, -- صلاحية الاشارة (مثلا 24 ساعة) created_at TIMESTAMPTZ DEFAULT now(), updated_at TIMESTAMPTZ DEFAULT now() ); -- فهرس للاستعلام السريع CREATE INDEX idx_signal_tracking_user_status ON signal_tracking(user_id, status); CREATE INDEX idx_signal_tracking_active ON signal_tracking(status) WHERE status IN ('active', 'pending');

الميزة الثالثة
مراقبة الاسعار الحية (Real-Time Price Monitor)
هذه الميزة مرتبطة ارتباطا وثيقا بدورة حياة الاشارات. مراقبة الاسعار تعني: عندما ينشئ المستخدم اشارة او يتابع تحليلا، يبدأ التطبيق في مراقبة سعر الزوج بشكل لحظي عبر WebSocket، وعندما يصل السعر لوقف الخسارة او الهدف يُرسل اشعار فوري.
الحالة الحالية: VIXOR لديه بالفعل كل ما يلزم لمراقبة الاسعار. BinanceWS (src/shared/market-data/binance-ws.ts) هو Singleton يربط بـ Binance WebSocket العام (بدون API key). useLivePrices (src/shared/market-data/use-live-prices.ts) هو هوك React يستخدم BinanceWS. هذا يعمل فعلا في الـ Dashboard لعرض اسعار العملات.
ما ينقص: وصل useLivePrices بنظام Signal Tracking بحيث يتم فحص كل تحديث سعر مقابل TP/SL الاشارات النشطة. هذا لا يحتاج اي بنية تحتية جديدة - فقط ربط المكونات الموجودة.
التصميم المستوحى من QuantDinger: في QuantDinger، المراقبة تعتمد على الـ Polling كل 5 دقائق (decide_interval). هذا بطيء جدا لتطبيق تليجرام حيث المستخدم يتوقع اشعارات فورية. في VIXOR سنستخدم WebSocket (الذي يعمل فعلا) للحصول على تحديثات لحظية ثم نُقارنها بـ TP/SL محليا على جهاز المستخدم.

الفصل التاسع
ما لن يتغير (حماية النظام)
قاعدة ذهبية: لا يتم حذف او تعديل اي ملف موجود الا اذا كان في قائمة "الملفات المتأثرة" اعلاه. المحرك التحليلي (analysis/engine/) لا يتغير. الـ API endpoints في server/api/ لا تتغير. الـ 33 صفحة الموجودة لا تُحذف ولا تُستبدل. كل صفحة "COMING SOON" تبقى كما هي.
ملفات لن تُمس: كل ملفات محرك التحليل (analysis/engine/)، كل ملفات الـ API (server/api/)، كل ملفات الـ Copilot، كل ملفات الـ Discovery، كل ملفات الـ Backtest، كل ملفات الـ Wallet، كل ملفات الـ Auth. هذه كلها تعمل ولا داعي لتعديلها.
صفحات لن تُمس: كل الصفحات الـ 33 الموجودة تبقى كما هي. التعديلات ستكون اضافات فقط (ازرار جديدة، عناصر مرئية اضافية) وليس استبدالات.
الفصل العاشر
مصفوف المخاطر والتخفيف
المخاطرةالاحتمالالتخفيف
تعديل ملف موجود يكسر صفحة متوسط كل تعديل يكون اضافة (additive) وليس استبدال. لا نُعدل منطق موجود، نُضيف عليه فقط.
الـ WebSocket يستهلك بطارية عالية منخفض الاشتراك محدود بازواج الاشارات النشطة فقط (5-10 ازواج عادة). BinanceWS يدعم Reconnect تلقائي.
Migration SQL يفشل في Supabase متوسط Migration بسيط (جدول واحد + فهرسين). لا يُعدل جداول موجودة. يمكن التراجع بسهولة.
تحديث types.ts يتعارض مع Supabase منخفض Types تُولّد من Supabase. بعد تنفيذ Migration، نُعيد توليد Types via CLI.
رابط المشاركة على X لا يعمل داخل تليجرام متوسط تليجرام يفتح الروابط في متصفح داخلي. X intent links تعمل في المتصفح. سنضيف fallback لـ "نسخ النص" ايضا.
Bundle size يزيد بسبب ملفات جديدة منخفض الملفات الجديدة صغيرة (200-400 سطر لكل ملف). لا نُضيف مكتبات جديدة. كل شيء يستخدم الموجود.
